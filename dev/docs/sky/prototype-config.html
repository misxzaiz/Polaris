现状：config 读写的多个入口 扩散面

config 是 config.json 单一真源，但写它的通道不止一条。每多一条通道，就多一份语义漂移风险。
⚠️ 不只三份，是 四通道：httpTransport.ts:31-33 把 get_config/update_config/update_config_patch 统一映射到 /api/settings（GET / PATCH 双方法），摘旧时这条映射必须一并切 dispatch，否则 Web 端 config 读写整条断裂。

非命令壳但直读 config_store 隐藏漂移源

这些点不是命令壳，不随「摘旧」一起消失 —— 摘壳后若不逐个核对，旁路直读仍在，双通道并未真正关闭。

cap.config —— 管理面唯一入口 同步能力

注册于 state.rs 装配点（与 cap.kv/todo/context 并列）。动作协议一次定稿，payload 即契约。

动作面

副作用链（sky 没有，Polaris 必须做）

⚠️ cap.config 与 sky ConfigTool 的本质差异：sky 写后不热更新（需重启），Polaris 的 patch 必须顺序触发「级联 settings.json → 刷新引擎缓存 → emit config-changed → 启停 web」。副作用链断一环，config 的「改即生效」语义就丢。

白名单 schema 模型 单一真源

复用 sky 的 field_schemas()/apply_patch() 双端一致性范式，但 sections 从 sky 的 4 字段扩为可写 section 建模 —— 41 个顶层字段不能全部开放写。
section类型权限说明
敏感字段读路脱敏（复用 mask_key：`${ENV}`→`env:<NAME>`，≤4 字符全遮，否则 `****<后4字符>`）；Secret/Path 型写走独立动作或二次授权；dispatch 审计沿用「source 只落变体名」惯例，永不落明文。

PolicyPermission 权限矩阵 阶段 C 启用

第五步已预埋 cap.config → remote deny（policy_permission.rs:236-272）。Bootstrap（桌面主窗口）不受限；Remote（Web/browser）对管理面拒绝；精确规则 cap.config.read 可覆盖通配 deny 放行只读。
