# 地基级改造方案：跨界启发与深度复审

> 状态：分析中，暂不实施
> 创建：2026-09-27
> 前置文档：`00-总体规划.md`、`01-根因分析.md`、`02-触发全景图.md`

## 一、当前方案的真实缺陷（诚实复审）

### 缺陷 1：SessionKernel 仍然是一个"上帝接口"

当前 `SessionKernel` interface 包含了 sendMessage / continueChat / interrupt / regenerate / editAndResend / createSession / deleteSession / switchSession / getActiveSessionId / getSessionMetadata / listSessions / getSessionState / getSessionSnapshot / getMessages / handleEvent / subscribe / restoreFromHistory / resyncSession —— **17 个方法**。

这不是"内核"，是一个把 sessionStoreManager + createConversationStore + eventHandler + historyService + webReconnectResync 的功能全部塞进一个 interface 的"大杂烩"。任何一个方法签名变动都要改实现，这恰恰是上一版"8 模块过度拆分"的反面——**从过度拆分走向了过度聚合**。

### 缺陷 2：Message Model 的状态机是"画给文档看的"，不是"代码能执行的"

当前定义了 `drafted → sending → active → streaming → settled → persisted → restored` 7 个状态，但这只是 ASCII 图。真正的问题是：

- 谁来执行状态转换？前端还是后端？
- 转换是同步的还是异步的？
- 非法转换（如从 settled 直接回到 sending）由谁拒绝？
- 状态转换失败时回滚到哪个状态？

没有定义转换函数和守卫条件，这个状态机就是装饰性的。

### 缺陷 3：把"后端权威"当作银弹

方案说"后端是权威源，前端只持有快照"，但忽略了：

- **后端也可能崩溃**（进程退出、服务重启），EventBroadcaster 的重放缓冲是纯内存的
- **快照拉取有延迟**，A 发消息后 1ms，B 拉快照可能拿不到这条消息（还没落盘）
- **不是所有状态都适合后端权威**：输入草稿、可见区域、UI 滚动位置等纯前端状态，强行后端化会增加不必要的网络往返

需要区分"哪些状态后端权威"和"哪些状态前端权威"，而不是一刀切。

### 缺陷 4：没有定义"扩展点"

用户说"支持类似插件的方式随意替换"，但当前方案只有 LegacyKernel 和 V2Kernel 两个实现，没有定义第三方怎么写自己的实现。`registry.ts` 说"注册中心"但没说注册什么、怎么注册、插件和内核的关系是什么。

真正的插件化需要一个**扩展点契约**：内核提供什么 hook，插件可以 intercept 什么，内核怎么发现插件，插件之间怎么隔离。

## 二、跨界启发：从其他领域看"地基怎么打"

### 启发 1：Minecraft 的模组机制

Minecraft 的模组体系经过 15 年演化，是"插件化地基"最成熟的实践之一。

**核心设计**：

1. **游戏引擎不知道模组存在**。引擎只定义"事件"（玩家放置方块、实体受伤、世界加载完成），模组订阅事件。引擎不 import 模组，模组 import 引擎。

2. **事件总线是唯一的交互通道**。模组不能直接调引擎内部方法，只能通过事件总线通信。这保证了引擎内部重构不影响模组。

3. **注册表模式**。模组注册自定义方块/物品/实体到全局注册表，引擎通过注册表查找。注册表是"内核数据"，但注册动作是"模组行为"。

4. **加载阶段严格分层**：
   - `PRE_INIT`：模组注册自己的内容到注册表
   - `INIT`：模组间互相发现，建立依赖
   - `POST_INIT`：所有注册完成，开始运行
   - 越界的注册直接拒绝（POST_INIT 阶段不能再注册方块）

5. **冲突仲裁**。两个模组注册同一个 ID → 最后注册的覆盖，前一个收到冲突通知。不是报错，是"可恢复的冲突"。

**对 Polaris 会话体系的启发**：

| Minecraft 概念 | Polaris 对应 | 当前方案的问题 |
|---|---|---|
| 事件总线 | AIEvent 流 | 当前有事件总线，但会话状态不在事件总线上 |
| 注册表 | 会话注册表 | 当前 SessionStoreManager 既是注册表又是状态机 |
| 模组不能调引擎内部 | 插件不能直接改 messages 数组 | 当前没有这层隔离 |
| 加载阶段分层 | 会话生命周期阶段 | 当前没有"在什么阶段允许做什么"的约束 |
| 冲突仲裁 | 跨设备并发冲突 | 当前没有"可恢复冲突"概念，直接丢数据 |

### 启发 2：Git 的对象模型

Git 是另一个经过 20 年验证的"数据地基"。

**核心设计**：

1. **内容寻址**。每个对象（blob/tree/commit）的 ID 是内容的 SHA-1。相同内容永远得到相同 ID，不需要中心化分配。

2. **不可变对象 + 可变引用**。对象一旦创建不可修改（改了就变成新对象，新 ID）。引用（branch/tag）是可变的指针，指向某个对象。

3. **三方合并**。冲突不是"报错"，是"产生一个合并状态，需要解决"。合并是基于三方（base/ours/theirs）的差异计算。

4. **快进 vs 合并**。如果没有分叉，更新就是快进（移动指针）；有分叉才需要合并。

**对 Polaris 会话体系的启发**：

| Git 概念 | Polaris 对应 | 启发 |
|---|---|---|
| 内容寻址 | 消息 ID | 当前用 clientMessageId（设备生成的 UUID），但后端可以改写内容。如果消息 ID = content hash，则"相同内容必然相同 ID"，跨设备自然去重 |
| 不可变对象 + 可变引用 | 消息不可变 + 会话是消息的有序引用 | **当前最大的设计问题：消息是可变的**（eventHandler 会修改消息的 blocks、压缩器会修改 content）。如果消息一旦创建就不可变，会话只是一个有序的消息 ID 列表，并发问题大幅简化 |
| 三方合并 | 跨设备冲突 | 当前方案用"后端排他锁"解决并发，但如果用三方合并，A/B 可以同时编辑，最后合并时自动解决大部分冲突 |
| 快进 | 单设备追加消息 | 只追加不修改时，更新就是快进，无需锁 |

**最重要的启发**：**消息应该是不可变的**。当前系统允许修改消息（压缩、回填 diff、更新 tool_call 状态），这是并发问题的根源之一。如果消息不可变，"修改"=创建新版本（新 ID），会话引用新版本而不是旧版本，旧版本保留在历史中。

### 启发 3：CRDT（Conflict-free Replicated Data Type）

CRDT 是分布式系统中的"免协调数据结构"，代表项目：Automerge、Yjs。

**核心设计**：

1. **每个操作有因果序**。操作携带 Lamport 时间戳或向量时钟，不依赖中心化 seq。
2. **合并是确定性的**。任何两个设备执行相同操作集，最终状态相同，不需要协调。
3. **操作幂等**。同一操作执行多次，结果相同。
4. **支持离线**。设备可以离线执行操作，上线后合并，不丢数据。

**对 Polaris 会话体系的启发**：

当前用"后端 seq + 重放缓冲"做同步，这是"中心化 seq"模型。CRDT 的启发是：

- **消息追加是天然 CRDT**。"把消息 M 追加到会话 C"这个操作是幂等的（按 messageId 去重），因果序天然（消息有 timestamp），合并是确定性的（按 timestamp 排序）。
- **不需要排他锁**。两个设备同时追加消息，合并时按 timestamp 排序即可，不需要一个等待另一个。
- **但"状态修改"不是 CRDT**。"把 isStreaming 从 true 改为 false"这个操作不能幂等合并（A 设 false 然后 B 也设 false 是对的，但 A 设 false 然后 B 设 true 是冲突）。所以 streaming 状态不适合 CRDT，需要后端权威仲裁。

### 启发 4：操作系统的进程隔离

操作系统用了 60 年的"进程隔离"模型：

1. **每个进程有自己的地址空间**。进程 A 不能直接读写进程 B 的内存。
2. **通过 IPC 通信**。管道、信号、共享内存、消息队列。
3. **内核是唯一的协调者**。进程不直接协调，都通过内核。
4. **能力（capability）而非身份**。进程不检查"你是谁"，检查"你有没有权限做这件事"。

**对 Polaris 的启发**：

当前所有会话共享同一个 Zustand store 实例的内存空间，任何代码都能直接 `store.setState({ messages: [...] })` 覆盖。操作系统模型启发我们：

- **每个会话应该有自己的"地址空间"**。外部代码不能直接 `store.setState`，只能通过会话自己的接口操作。
- **会话间通过事件通信**，不通过共享状态。
- **能力检查**。"这个设备有没有权限中断这个会话"——当前完全不检查，B 设备可以中断 A 发起的会话。

### 启发 5：银行账本的 append-only 模型

银行账本是金融领域最成熟的"不可丢数据"系统：

1. **只追加不修改**。一笔交易一旦入账，永远不修改。如果错了，追加一笔"冲正"交易。
2. **余额是计算结果**。不是存储值。余额 = 所有关联交易的代数和。
3. **对账是常态**。定期比对两份账本（如银行 vs 商户），差异触发调查。
4. **日志即真相**。所有操作都记入日志，日志是审计的唯一依据。

**对 Polaris 的启发**：

- **消息流应该是 append-only**。不允许修改已存在的消息（压缩、回填 diff 都应该是追加"修订记录"而非修改原始消息）。
- **会话的"当前状态"是计算结果**。isStreaming = "最近一条事件是 session_start 且没有对应的 session_end"，而不是一个存储值。
- **对账机制**。定期比对前端消息列表和后端持久化，差异触发快照同步。

## 三、综合：修正后的地基设计

综合以上启发，地基应该从"一个 17 方法的 SessionKernel interface"修正为**3 层架构**：

```
┌──────────────────────────────────────────────────────────────┐
│                     UI / Hooks 层                             │
│              （通过 Capability 访问，不直接操作 store）         │
└──────────────────────┬───────────────────────────────────────┘
                       │
┌──────────────────────┴───────────────────────────────────────┐
│              扩展层（Extension Layer）                        │
│                                                          ┌───┤
│  Event Bus（事件总线，唯一交互通道）                     │插件│
│  • 消息生命周期事件                                     │注册│
│  • 会话状态变化事件                                     │区 │
│  • 冲突事件                                             │   │
│                                                          └───┤
└──────────────────────┬───────────────────────────────────────┘
                       │
┌──────────────────────┴───────────────────────────────────────┐
│              核心层（Core Layer）                              │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  Append-Only Message Log（不可变消息日志）              │    │
│  │  • 消息一旦写入不可修改（内容寻址 ID）                 │    │
│  │  • "修改"= 追加修订记录，引用原始消息                  │    │
│  │  • 按 messageId 幂等                                   │    │
│  │  • 按 (conversationId, timestamp) 全局有序            │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  Session Registry（会话注册表）                        │    │
│  │  • 会话 = 有序的消息 ID 列表（引用，不存内容）         │    │
│  │  • 会话元数据（标题、工作区、引擎等）                  │    │
│  │  • 注册表只做 CRUD，不做状态机                        │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  State Authority（状态仲裁器，后端权威）               │    │
│  │  • 接收状态查询（isRunning, currentMessages）          │    │
│  │  • 接收状态修改请求（start, interrupt）                │    │
│  │  • 仲裁冲突（两个设备同时操作同一会话）                │    │
│  │  • 状态 = 从消息日志 + 操作日志计算                    │    │
│  └──────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

### 第一块砖：Append-Only Message Log

借鉴银行账本 + Git 不可变对象 + CRDT 幂等追加：

**数据模型**：

```
MessageEntry {
  id: string           // messageId，全局唯一，创建方生成
  conversationId: string
  role: 'user' | 'assistant' | 'system'
  timestamp: number    // 创建方时间戳，用于因果序
  deviceId: string     // 创建方设备标识
  content: JSON        // 完整消息内容（blocks/attachments）
  version: number      // 内容版本（修订时递增）
  parentVersion?: number // 修订前版本（链式修订）
}
```

**操作**：

| 操作 | 语义 | 并发安全 |
|---|---|---|
| `append(entry)` | 追加新消息 | 幂等（按 id 去重），无需锁 |
| `revise(id, newContent)` | 追加修订记录 | 新版本号，旧版本保留 |
| `read(conversationId, fromSeq?, limit?)` | 读取消息 | 只读，无锁 |

**关键约束**：
- 不存在"修改消息"操作。压缩/回填 diff/状态更新都是追加修订。
- 消息内容是 JSON，支持部分修订（如只更新 tool_call 的 status 字段）。
- 后端 SQLite 按 messageId 做主键，INSERT OR IGNORE 实现幂等。

**为什么这是地基**：
- 跨设备并发写 = 两个 append 操作，按 messageId 去重，无冲突
- 崩溃恢复 = 重读日志，无状态需要恢复
- 消息完整性 = 日志即真相，不存在"内存态比磁盘新"的竞态

### 第二块砖：Session Registry

借鉴 Minecraft 注册表 + Git 可变引用：

**数据模型**：

```
SessionRecord {
  id: string               // 前端生成的会话 ID
  conversationId: string?  // 后端分配的引擎会话 ID（首次发消息后才有）
  title: string
  engineId: string
  workspaceId: string?
  metadata: JSON           // 工作区/模型/agent 等配置
  messageIds: string[]     // 有序的消息 ID 列表（引用 Message Log）
  createdAt: number
  updatedAt: number
}
```

**操作**：

| 操作 | 语义 |
|---|---|
| `create(record)` | 注册新会话 |
| `get(id)` / `list(filter)` | 查询 |
| `updateMetadata(id, patch)` | 更新元数据（标题/工作区等） |
| `appendMessageId(id, messageId)` | 向消息列表追加引用 |
| `delete(id)` | 删除会话（消息日志保留，只删引用） |

**关键约束**：
- Session Registry 只存引用，不存消息内容。消息在 Message Log 中。
- 会话的"当前消息列表" = `messageIds.map(id => messageLog.get(id))`，是计算结果。
- 追加引用是幂等的（messageId 已在列表中则跳过）。
- 会话元数据更新用 CAS 乐观锁（version 不匹配拒绝）。

**为什么这是地基**：
- 会话和消息解耦。会话删除不丢消息，消息追加不影响会话。
- 跨设备同步会话 = 同步 messageIds 列表（一个字符串数组），比同步完整消息轻量得多。
- 元数据持久化在后端 SQLite，重启不丢失。

### 第三块砖：State Authority

借鉴操作系统内核仲裁 + 银行对账：

**职责**：后端唯一的"会话运行状态仲裁者"。

**接口**：

```
StateAuthority {
  // 查询：计算当前状态（不是存储值）
  getSessionStatus(conversationId): { running: boolean, lastEventSeq: number }
  // 请求：发起操作（后端仲裁后才执行）
  requestStart(conversationId, message): { ok: boolean, reason?: string }
  requestInterrupt(conversationId, deviceId): { ok: boolean, reason?: string }
  // 对账：比对前端快照与后端真实状态
  reconcile(conversationId, clientSnapshot): { missing: MessageEntry[], extra: MessageEntry[], statusMismatch: boolean }
}
```

**关键设计**：
- `getSessionStatus` 返回的是**计算结果**：`running = 存在 session_start 事件但无对应 session_end`。不是存储值。
- `requestStart` 是**仲裁**：检查"这个会话是否已经 running"，如果是则拒绝（不是排队等待，是直接拒绝并返回原因）。
- `requestInterrupt` 检查**能力**：`deviceId` 是否有权限中断（是发起方设备或全局管理员）。
- `reconcile` 是**对账**：前端定期或断线后调用，比对本地消息列表与后端日志，找出差异。

**为什么这是地基**：
- 状态是计算结果不是存储值 → 不存在"状态不一致"问题（状态永远是从日志算出来的）
- 仲裁在后端 → 跨设备冲突在后端解决，前端不需要协调
- 对账机制 → 提供了一个"最终一致"的兜底，即使中间出了任何问题，对账能发现并修复

## 四、与当前方案的对比

| 维度 | 前一版方案 | 修正后方案 |
|---|---|---|
| 接口数量 | 1 个 SessionKernel（17 方法） | 3 个核心组件（Message Log 3 方法 + Registry 5 方法 + Authority 3 方法） |
| 消息模型 | 可变（eventHandler 可修改 blocks） | **不可变**（append-only，修订追加新版本） |
| 状态来源 | 后端存储 isStreaming 值 | 后端从事件日志计算 isStreaming |
| 并发策略 | 排他锁（B 等待 A 完成） | append 天然无锁 + 状态操作仲裁 |
| 恢复策略 | 快照拉取 + 合并 | 对账（reconcile）计算差异，确定性修复 |
| 插件扩展 | 未定义 | 事件总线 hook + 注册表注册 |
| 跨设备消息 ID | clientMessageId（设备生成 UUID） | messageId（设备生成，幂等去重） |
| LRU 驱逐 | 冻结模式 | 不需要（会话是引用，不占内存） |

## 五、插件化扩展点设计（借鉴 Minecraft）

### 扩展点 1：事件 Hook

插件可以订阅和拦截会话事件：

```
// 插件注册示例
registerPlugin({
  id: 'my-session-monitor',
  
  // 生命周期 hook：会话创建前
  beforeCreateSession(record: SessionRecord): SessionRecord | null {
    // 可以修改 record（如注入自定义 metadata）
    // 返回 null 阻止创建
    return record
  },
  
  // 生命周期 hook：消息追加前
  beforeAppendMessage(entry: MessageEntry): MessageEntry | null {
    // 可以修改消息内容（如过滤敏感信息）
    // 返回 null 阻止追加
    return entry
  },
  
  // 事件 hook：会话状态变化
  onSessionStatusChange(conversationId: string, old: SessionStatus, new: SessionStatus): void {
    // 通知外部系统
  },
})
```

### 扩展点 2：存储后端可替换

Message Log 和 Session Registry 的存储后端通过 interface 隔离：

```
interface MessageLogStorage {
  append(entry: MessageEntry): Promise<void>      // 幂等
  read(conversationId: string, opts?): Promise<MessageEntry[]>
  revise(id: string, newContent: JSON): Promise<void>
}

// 默认实现：后端 SQLite
class SqliteMessageLog implements MessageLogStorage { ... }

// 插件实现：云端同步
class CloudMessageLog implements MessageLogStorage { ... }
```

### 扩展点 3：状态仲裁策略可替换

```
interface StateArbiter {
  canStart(conversationId: string, deviceId: string): boolean
  canInterrupt(conversationId: string, deviceId: string): boolean
}

// 默认：后端排他仲裁
class BackendArbiter implements StateArbiter { ... }

// 插件：多设备协作模式（允许多设备同时查看但不允许同时操作）
class CollaborativeArbiter implements StateArbiter { ... }
```

### 加载阶段（借鉴 Minecraft 的 PRE_INIT / INIT / POST_INIT）

```
Phase 1 — REGISTER: 插件注册自己 + 注册自定义存储后端
Phase 2 — WIRE: 插件建立依赖关系（如"我的插件需要在存储插件之后加载"）
Phase 3 — RUN: 所有注册完成，开始处理会话事件
  → Phase 3 之后不允许注册新插件（避免运行时注入）
```

## 七、待决策问题（需要进一步讨论）

1. **消息不可变 vs 可变**：当前 eventHandler 会实时修改消息的 blocks（追加 tool_call、更新 thinking 等）。如果消息不可变，这些"实时修改"需要改为"追加修订"。这是否会影响流式渲染性能？（流式时每秒可能产生几十个 delta）

2. **对账频率**：reconcile 是每次断线后调一次，还是定期心跳调？定期调会增加后端负载。

3. **修订链的深度**：一条消息被压缩后又被恢复，再被压缩……修订链会无限增长吗？需要 GC 策略吗？

4. **插件隔离级别**：插件崩溃是否应该隔离（不影响主流程），还是直接抛错？Minecraft 的做法是模组崩溃会踢出整个游戏，但我们可能需要更宽容的策略。

5. **messageIds 列表的增长**：一个大会话可能有几千条消息，SessionRegistry 的 messageIds 数组会很大。是否需要分页存储？
