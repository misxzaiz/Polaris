## 案例 5：插件扩展点覆盖 — ✅ 通过

**验证假设**：事件 hook + 存储可替换 + 仲裁策略可替换，能覆盖全部 6 类 AI 对话触发点

### 测试结果

```
✓ 17 tests passed (49ms)
```

### 验证项

| 场景 | 插件模拟 | 结果 | 说明 |
|---|---|---|---|
| 1. 用户直接交互 | UserInteractionPlugin：beforeAppendMessage 注入 workspacePrompt + onSessionStatusChange 更新 UI | ✅ | sendMessage 路径完整复现 |
| 1b. 消息拦截 | SensitiveGuardPlugin：beforeAppendMessage 返回 null | ✅ | 敏感词阻止追加 |
| 1c. 多插件链式 | 两个插件依次修改 entry，结果串联 | ✅ | hook 链式传递正确 |
| 2. 后台静默会话 | SilentSessionPlugin：silentMode 跳过 UI 激活 + session_end 触发标题生成 | ✅ | titleGeneration 路径完整复现 |
| 2b. 创建拦截 | BlockerPlugin：beforeCreateSession 返回 null | ✅ | 无工作区不允许创建 |
| 3. 调度器 | SchedulerPlugin：session_end 区分 done/failed 更新任务 | ✅ | 任务状态路由正确 |
| 4. 历史恢复 | HistoryRestorePlugin：beforeCreateSession 挂 messageIds | ✅ | 恢复后消息可读取 |
| 5. 引擎直接调用 | EngineDirectPlugin：assistant 消息注入 contextId 路由 | ✅ | 引擎层消息正确落库 |
| 6. isStreaming 消费方 | StreamingConsumerPlugin：running 变化触发自动滚动/TTS/提交信息 | ✅ | 8 个消费方各自订阅模式可复现 |
| 6b. 异步 hook | AsyncConsumerPlugin：await 异步消费方 | ✅ | 异步 TTS/标题生成可支持 |
| 7. 仲裁策略替换 | CollabPolicyPlugin：beforeRequestStart 拒绝非 master 设备 | ✅ | 自定义仲裁可注入 |
| 加载机制 | 三阶段 register→wire→run | ✅ | run 后禁止注册 |
| 加载机制 | 重复注册/依赖不存在/依赖成环 | ✅ | 全部抛错 |
| 加载机制 | 依赖拓扑排序 | ✅ | 依赖方排在依赖项之后 |
| 加载机制 | run 前分发 hook 抛错 | ✅ | 防止插件未就绪被调用 |

### 关键结论

1. **假设 5 成立**：4 个 hook（beforeCreateSession / beforeAppendMessage / onSessionStatusChange / beforeRequestStart）+ 存储可替换 + 仲裁可替换，覆盖全部 6 类触发场景
2. **hook 语义清晰**：before* 是拦截器（返回 null 阻止），on* 是订阅器（异步允许），拦截器链式传递、订阅器广播分发
3. **Minecraft 三阶段加载验证可行**：register 阶段后禁止注册，依赖拓扑排序与成环检测有效，防止运行时注入
4. **异步 hook 必须支持**：标题生成、TTS、提交信息订阅都是异步消费方，OnSessionStatusChangeHook 返回 `void | Promise<void>` 验证通过
5. **仲裁策略扩展点比 beforeRequestStart 更贴近"后端权威"**：beforeRequestStart 是纯前端策略钩子，真正的仲裁仍在 StateArbiter（事件日志计算），两者可组合

### 发现的设计改进

1. **命名对齐**：设计文档中 hook 名为 `onSessionStatusChange`，初版 types.ts 用了 `onStatusChange`，已统一为前者
2. **dispatch 需检查 phase**：`dispatchBeforeCreateSession` 等在非 run 阶段应抛错而非静默通过，防止插件未就绪时被调用（Minecraft 同理：模组未加载完不允许交互）

### 验证项

| 场景 | 结果 | 说明 |
|---|---|---|
| Message 正常生命周期 drafted→…→persisted | ✅ | 7 状态全链路 |
| sending 不能直接 streaming（跳过 active） | ✅ | 守卫拒绝 + 保持原状态 |
| settled 不能回到 sending（定稿后不可重发） | ✅ | 消息不可变语义 |
| persisted 不能变回 streaming（落盘后不可变） | ✅ | |
| active 需要 conversationId（后端确认） | ✅ | guard 生效 |
| 失败转换不产生部分状态（原子性） | ✅ | conversationId 不污染 |
| restored 通配转换（任何状态可被恢复覆盖） | ✅ | from 省略 = 通配语义 |

| idle 不能直接 error（只有 running 才能 error） | ✅ | |
| error→idle 恢复后可继续发消息 | ✅ | |
| 多轮会话第二轮 running | ✅ | |
| canTransition 预检含 guard | ✅ | 修正：同时检查白名单 + guard |

### 关键结论

1. **可执行状态机成立**：转换表 + 守卫 + 原子性回滚三者齐备，非法转换被明确拒绝并保持原状态
2. **能力接口替代上帝接口成立**：6 个能力接口（消息发送/会话生命周期/状态查询/事件处理/恢复同步/仲裁策略）各自 ≤5 个方法，消费方只注入需要的能力
3. **`from` 省略 = 通配** 比"空数组 = 拒绝所有"更符合直觉：`restored` 覆盖语义（恢复可覆盖任何本地状态）用通配表达
4. **canTransition 必须含 guard 预检**：只查白名单会误报"idle 可创建"（实际缺 conversationId）
