## 案例 1：并发 append 零丢失 — ✅ 通过

**验证假设**：append-only 消息日志能解决并发写丢失

### 测试结果

```
✓ 16 tests passed (67ms)
  - 1000 条并发 append: 35.2ms (< 100ms ✓)
  - 100 次连续 revise: 1.8ms (< 50ms ✓)
```

### 验证项

| 场景 | 结果 | 说明 |
|---|---|---|
| 单设备追加 100 条 | ✅ | 读取到 100 条 |
| 消息按 timestamp 升序 | ✅ | 乱序写入也能正确排序 |
| 两设备并发各写 100 条 | ✅ | 最终 200 条无重复 |
| 两设备并发写相同 ID | ✅ | 幂等去重，只保留 1 条 |
| 两设备并发写相同 ID 不同 content | ✅ | 先到先得，只保留 1 条 |
| 不同会话消息互不干扰 | ✅ | 按 conversationId 隔离 |
| revise 追加新版本旧版本保留 | ✅ | 修订链完整 |
| read 返回最新版本 | ✅ | 不返回历史版本 |
| 1000 条并发 append 性能 | ✅ 35.2ms | 远低于 100ms 阈值 |
| 100 次 revise 性能 | ✅ 1.8ms | 远低于 50ms 阈值 |
| read with afterTimestamp | ✅ | 增量读取正确 |
| read with limit | ✅ | 分页正确 |
| deleteByConversation | ✅ | 只删目标会话，不影响其他 |
| 空会话 read | ✅ | 返回空数组 |
| revise 不存在的消息 | ✅ | 抛错 |
| getLatest 不存在的消息 | ✅ | 返回 null |

### 关键结论

1. **假设 1 成立**：append-only + messageId 幂等去重能解决并发写丢失，不需要排他锁
2. **修订链性能达标**：100 次 revise 1.8ms，流式渲染期间追加修订完全可行，不需要"流式期间可变"折中
3. **幂等去重可靠**：两设备同时写相同 messageId，只保留一个，不报错不丢失

## 案例 3：状态从日志计算 — ✅ 通过

**验证假设**：状态从事件日志计算比存储值更可靠

### 测试结果

```
✓ 21 tests passed (54ms)
  - 1000 条事件 getStatus: 0.44ms (< 5ms ✓)
```

### 验证项

| 场景 | 结果 | 说明 |
|---|---|---|
| 无事件 → running=false | ✅ | 空状态正确 |
| 只有 session_start → running=true | ✅ | 从日志推导 |
| start → end → running=false | ✅ | 配对检测 |
| start → error → end(reason=error) | ✅ | error 信息正确传递 |
| 多轮会话第二轮 start | ✅ | 正确识别最新轮次 |
| 多轮会话第二轮 start → end | ✅ | running=false |
| 跨设备：A 发起 → B 查询 | ✅ | B 得到正确 running=true |
| 跨设备：A 发起 → A 结束 → B 查询 | ✅ | B 得到正确 running=false |
| 崩溃：有 start 无 end → running=true | ✅ | 诚实反映不确定状态 |
| 崩溃恢复：后端补插 end | ✅ | running=false，error 有值 |
| requestStart 已 running → 拒绝 | ✅ | 仲裁生效 |
| requestStart idle → 允许 | ✅ | |
| requestInterrupt running → 允许 | ✅ | |
| requestInterrupt idle → 拒绝 | ✅ | |
| 两设备同时 requestStart | ✅ | 只有一个成功 |
| readAfterSeq 增量恢复 | ✅ | 按 seq 过滤 |
| readAfterSeq(0) 全量 | ✅ | |
| 1000 条事件计算性能 | ✅ 0.44ms | 远低于 5ms |
| 相同事件 ID 幂等 | ✅ | 重复追加跳过 |
| 不同会话隔离 | ✅ | |
| deleteByConversation | ✅ | 只删目标会话 |

### 关键结论

1. **假设 3 成立**：`isRunning = 存在 session_start 但无配对 session_end`，从事件日志计算完全可靠
2. **性能极佳**：1000 条事件 getStatus 仅 0.44ms，不需要物化视图缓存
3. **崩溃恢复方案可行**：后端启动时扫描无配对 session_start 的会话，补插 session_end(reason=error)，状态自动修正
4. **跨设备一致性天然保证**：所有设备查同一份事件日志，计算结果必然相同
