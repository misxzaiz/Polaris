### 关键设计

1. **后端权威不读本地**：`getSessionState` 有 conversationId 时调 `session_get_status`（V2StateArbiter），running/error/idle 由后端 `SessionStatus` 推导；无 conversationId 用本地兜底；会话不存在返回 none
2. **订阅双通道**：`subscribe` 复用 kernel 的 store/manager 双通道事件驱动 + 运行中轮询（1s），后端状态变化触发 handler；消费方统一经 `subscribeKernelSessionState`（handler 收到推导后的 `{ state, isStreaming, error }`）
3. **快照合并幂等**：`resyncSession` 按消息 id 去重，只追加缺失；恢复期间新事件产生的消息（本地已有）不覆盖 —— 对齐文档案例 4「恢复期间新事件不丢」
4. **竞态兜底**：`waitKernelSessionStreamEnd` 订阅后先查一次当前状态，已 idle 立即 resolve（对齐旧 `waitForIdle` 语义，避免挂起）
5. **保留 store 快照回退**：8 个消费方改造均保留本地 store 订阅兜底（渲染合并层 / 消息文本仍从 store 取），仅**流式状态源**切到内核 —— 降低回归风险

### 排他锁接入（本阶段核心改动）

**决策**：排他锁在 `cap.ai.chat` 的 start/continue 分支（dispatch 入口）强制接入，
而非仅依赖前端调用 `session_request_start` 预检——前端预检是体验层，后端事务化占位是强一致权威。

**实现**（3 个文件）：

| 文件 | 改动 |
|---|---|
| `src-tauri/src/services/session_state.rs` | 新增 `SessionStateDb::try_start_conversation`：**Immediate 事务**内完成「running 检查 + session_start 占位写入」原子操作。返回 `Ok(None)` 占位成功 / `Ok(Some(reason))` 已 running 被拒（reason 含启动方设备/时间） |
| `src-tauri/src/commands/session_state_commands.rs` | 新增 `session_try_start_inner`：供 capability 调用（复用命令层 db 单例 + `chrono::Utc::now` 时间戳） |
| `src-tauri/src/services/router/ai_chat_capability.rs` | `cap.ai.chat` 的 `invoke`/`invoke_stream` 两个 **continue** 分支接入 `session_try_start_inner`（start 分支无 conversationId——引擎生成，新会话天然独立，不共享锁域）；continue 失败时**补偿写 session_end(error)** 释放占位，避免引擎未启动时占位卡 running 永久锁死 |

**关键设计**：

1. **为什么用 Immediate 而非 deferred 事务**：deferred 事务先读后写，读检查不持有
   写锁 → 双设备并发时两个请求都可能通过检查再各自写 start → 双 running 起点。
   Immediate 事务开启即抢写锁，后到者在 busy_timeout 内等待前者「检查+写入」原子
   完成后重读到 running → 被拒。这是排他锁正确性的核心。
2. **占位与引擎事件共存**：占位 start 由锁写入（id `req-<conv>-<uuid>`），引擎自身
   的 SessionStart/SessionEnd 仍由业务核 event_callback 追加（id `core-*`）。两条 start
   不影响 `compute_status_from_events`（只认最后一个 start 之后的 end）。
3. **失败补偿**：continue 的 `continue_chat_inner` 若引擎 spawn 失败（CLI 不可用等）
   不会触发引擎 SessionEnd → 占位卡 running。capability 层捕获错误后补写
   `session_end(reason=error)` 配对释放，锁可再次获取。

**flaky 根治**（本次发现并修复的既有基建缺陷）：

1. `tune_pragmas` pragma 顺序修正——`busy_timeout` 提到 `journal_mode=WAL` 之前

   （双设备冷启动）时后到者此前无 busy 等待直接报 `database is locked`。这是**产品真实
   竞态**，修复后并发 open 安全。
2. 集成测试共享 data_root 竞态——测试文件内 `data_root()` 为 OnceLock（首个 env 生效），
   各测试 `remove_dir_all` 重建目录会删除其他并行测试持有的 db 文件。改为进程级固定根
   目录（测试间不删除，conversation_id 已唯一）+ 全局串行锁，15 连跑零 flaky。
