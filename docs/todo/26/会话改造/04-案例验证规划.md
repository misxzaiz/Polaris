# 案例验证规划

> 状态：规划中，暂不实施
> 创建：2026-09-27
> 前置文档：`00-总体规划.md`、`01-根因分析.md`、`02-触发全景图.md`、`03-地基级改造方案.md`

## 一、为什么先做案例验证而不是直接实施

地基级改造涉及消息模型、状态权威、跨设备同步三个根本性变更。如果直接写实现再测试，一旦地基设计有误，所有上层实现都要返工。

案例验证的目标：**用最小代价验证地基设计的每个关键假设是否成立**，在写任何生产代码之前发现问题。

## 二、验证什么（5 个关键假设）

从 `03-地基级改造方案.md` 提取 5 个未经实践验证的核心假设，每个都需要用案例证明或证伪：

### 假设 1：append-only 消息日志能解决并发写丢失

**假设**：两个设备同时 append 消息到同一会话，按 messageId 幂等去重，不丢数据、不需要锁。

**验证方式**：写一个并发测试，两个"设备"（两个测试实例）同时往同一个 MessageLog 追加 100 条消息，验证最终读取到的消息数量 = 200，无重复、无丢失。

**如果不成立**：可能需要退回到后端排他锁模型。

### 假设 2：消息不可变 + 修订链不会导致性能问题

**假设**：流式渲染期间每秒产生几十个 delta，如果每个 delta 都是"追加修订"，修订链会很长但不会影响性能。

**验证方式**：模拟一次 AI 回复（100 个 token delta），用 append-only 模式追加 100 个修订，测量渲染性能和内存占用。对比当前"直接修改消息 blocks"模式的性能。

**如果不成立**：需要折中——流式期间消息可变，session_end 后冻结为不可变。

### 假设 3：状态从日志计算比存储值更可靠

**假设**：`isRunning = 存在 session_start 事件但无对应 session_end`，这个计算结果比存储一个 isStreaming 布尔值更可靠。

**验证方式**：模拟跨设备场景——A 设备发消息后断线，B 设备查询状态。验证 B 通过"从日志计算"得到的状态与后端真实状态一致。

**如果不成立**：如果计算成本太高或延迟太大，可能需要后端缓存计算结果（物化视图）。

### 假设 4：对账（reconcile）能发现并修复差异

**假设**：前端定期或断线后调 reconcile，比对本地消息列表与后端日志，找出缺失/多余消息并修复。

**验证方式**：构造一个"前端有 5 条消息、后端有 7 条"的差异场景，调 reconcile，验证前端正确补齐 2 条缺失消息。

**如果不成立**：如果差异计算过于复杂或网络往返过多，可能需要简化为"全量快照替换 + 增量事件流"。

### 假设 5：插件化扩展点能覆盖现有 6 类触发场景

**假设**：通过事件 hook + 存储可替换 + 仲裁策略可替换，能覆盖全部 6 类 AI 对话触发点（用户交互/静默会话/调度器/历史恢复/引擎层/isStreaming 消费方）。

**验证方式**：为每类触发点写一个"插件模拟"，验证通过扩展点能完整复现当前行为。

**如果不成立**：可能需要增加更多扩展点或调整接口设计。

## 三、验证策略：3 层验证

### 层 1：纯前端模拟验证（最快，无后端依赖）

用 Vitest + InMemoryBackend 模拟多设备。每个"设备"是一个独立的测试实例，共享同一个 InMemoryMessageLog（模拟后端）。

**优势**：不依赖 Rust 后端编译，几秒内跑完，可以快速迭代接口设计。

**验证内容**：
- 假设 1（并发 append 幂等）
- 假设 2（修订链性能）
- 假设 4（对账逻辑）
- 假设 5 的接口覆盖验证

### 层 2：后端 Rust 单元验证

在 `src-tauri/src/` 下用 `#[cfg(test)]` 模块验证后端 SQLite 层。

**优势**：验证真实持久化行为（SQLite + WAL），不依赖前端。

**验证内容**：
- 假设 1 的后端侧（SQLite INSERT OR IGNORE 幂等）
- 假设 3（状态计算逻辑）
- 文件锁（flock）并发安全

### 层 3：端到端集成验证

在 `src-tauri/src/web/integration_tests.rs` 中模拟双设备 HTTP+WS。

**优势**：最接近真实场景，验证全链路。

**验证内容**：
- 假设 3 的端到端侧
- 假设 4 的端到端侧
- 假设 5 的实际触发场景

## 四、案例清单

### 案例 1：并发 append 零丢失（验证假设 1）

**层 1 — 前端模拟**

```
准备：InMemoryMessageLog（共享实例）
设备A：并发 append 100 条消息（messageId = A1~A100）
设备B：并发 append 100 条消息（messageId = B1~B100）
验证：
  - log.read(conversationId) 返回 200 条
  - 无重复 messageId
  - 按 timestamp 排序后 A 和 B 消息交错
```

**层 2 — 后端 SQLite**

```
准备：临时 SQLite 文件
线程A：并发 INSERT OR IGNORE 100 条
线程B：并发 INSERT OR IGNORE 100 条
验证：
  - SELECT COUNT(*) = 200
  - 无重复 messageId
```

### 案例 2：修订链性能（验证假设 2）

**层 1 — 前端模拟**

```
准备：InMemoryMessageLog
操作：模拟流式回复
  - append 初始消息 M1（content = { text: "" }）
  - 100 次 revise(M1, { text: "累积到第N个字" })
  - 最终 M1 有 101 个版本
验证：
  - 读取最新版本 → content.text 完整
  - 读取修订历史 → 101 个版本，按 version 排序
  - 渲染性能：100 次 revise 的总耗时 < 50ms（jsdom 基准）
  - 内存占用：101 个版本的 JSON 总大小 < 100KB
对比：
  - 当前"直接修改 blocks"模式：100 次 setState 的总耗时
```

**关键决策点**：如果修订链性能不达标，在此案例中确认折中方案：
- 方案 A：流式期间可变，session_end 后冻结
- 方案 B：修订链超过 N 层时合并为快照（类似 Git 的 GC）

### 案例 3：状态从日志计算（验证假设 3）

**层 2 — 后端逻辑**

```
准备：session_events 表（session_start / session_end / error 事件）
场景 1（正常运行）：
  - insert session_start(seq=1)
  - insert session_end(seq=2)
  - 计算 get_status → { running: false, lastEventSeq: 2 }

场景 2（进行中）：
  - insert session_start(seq=1)
  - 计算 get_status → { running: true, lastEventSeq: 1 }

场景 3（崩溃后）：
  - insert session_start(seq=1)
  - 无 session_end（进程崩溃）
  - 计算 get_status → { running: true } ← 问题：如何区分"正在运行"和"崩溃"？
  - 补充：insert session_end(seq=2, reason=error) ← 由谁插入？

场景 4（跨设备查询）：
  - 设备A 的 session_start 在后端
  - 设备B 调 get_status → 需要返回 running: true
  - 验证延迟：< 5ms（SQLite 本地查询）
```

**关键决策点**：场景 3 暴露的问题——"崩溃后谁来插入 session_end？"。需要在此案例中确定：
- 方案 A：后端启动时扫描无配对 session_start 的会话，补插 session_end
- 方案 B：查询时加超时判断（session_start 后 N 秒无新事件视为崩溃）

### 案例 4：对账差异修复（验证假设 4）

**层 1 — 前端模拟**

```
准备：
  - InMemoryMessageLog（后端，有 7 条消息 M1~M7）
  - 前端快照（只有 5 条 M1~M5，模拟断线期间丢失了 M6~M7）

操作：reconcile(conversationId, clientSnapshot)
  - diff 后端 [M1~M7] vs 前端 [M1~M5]
  - 返回 { missing: [M6, M7], extra: [], statusMismatch: false }

验证：
  - 前端追加 M6, M7 后，再次 reconcile → { missing: [], extra: [], statusMismatch: false }
  - 无多余的消息被删���
```

**边界场景**：
```
场景 B（前端多出消息）：
  - 后端有 5 条 M1~M5
  - 前端有 7 条 M1~M7（用户在断线期间自己发了 M6~M7 但还没同步到后端）
  - reconcile → { missing: [], extra: [M6, M7] }
  - 不应删除 M6~M7（它们可能正在同步中），应标记为"待确认"

场景 C（状态不一致）：
  - 后端 status = idle（session_end 已落盘）
  - 前端 status = running（错过了 session_end 事件）
  - reconcile → { statusMismatch: true }
  - 前端应校正为 idle
```

### 案例 5：插件扩展点覆盖验证（验证假设 5）

**层 1 — 前端模拟**

为 6 类触发点各写一个"模拟插件"，验证通过扩展点能完整复现行为：

```
插件 1：UserInteractionPlugin
  - beforeAppendMessage hook：用户消息追加前注入 workspacePrompt
  - onSessionStatusChange hook：状态变化时更新 UI
  - 验证：sendMessage → 消息正确追加 + 状态变为 running

插件 2：SilentSessionPlugin
  - beforeCreateSession hook：silentMode 会话创建时跳过 UI 激活
  - onSessionStatusChange hook：session_end 时触发标题生成
  - 验证：标题生成会话正确创建和销毁

插件 3：SchedulerPlugin
  - onSessionStatusChange hook：session_end 时更新任务状态
  - 验证：调度任务执行后状态正确

插件 4：HistoryRestorePlugin
  - beforeCreateSession hook：从历史恢复时设置 messageIds
  - 验证：恢复后消息列表正确

插件 5：EngineDirectPlugin
  - beforeAppendMessage hook：引擎层直接调用时注入 contextId
  - 验证：引擎层消息正确路由

插件 6：StreamingConsumerPlugin
  - onSessionStatusChange hook：isStreaming 变化时触发 TTS / 自动滚动
  - 验证：8 个消费方行为正确
```

## 五、案例执行顺序与依赖

```
案例 1（并发 append）
  │ 不依赖其他案例
  ↓
案例 2（修订链性能）  ← 依赖案例 1 的 MessageLog 接口
  │
  ↓
案例 3（状态计算）    ← 不依赖前端，可与案例 2 并行
  │
  ↓
案例 4（对账）        ← 依赖案例 1 的 MessageLog + 案例 3 的状态计算
  │
  ↓
案例 5（插件覆盖）    ← 依赖案例 1~4 的接口已稳定
```

## 六、验证通过标准

每个案例必须满足：

| 标准 | 说明 |
|---|---|
| 功能正确 | 验证场景的所有断言通过 |
| 性能达标 | 前端操作 < 50ms，后端查询 < 5ms |
| 边界覆盖 | 正常 + 异常 + 空值场景都有测试 |
| 接口稳定 | 案例跑完后接口不需要修改（否则说明设计有误） |
| 可重复 | 测试可独立运行，不依赖外部状态 |

## 七、验证失败的处理

如果某个案例验证失败，不急于修复案例本身，而是回退到设计层面：

| 失败类型 | 处理 |
|---|---|
| 接口设计不合理（无法表达场景） | 修改 `03-地基级改造方案.md` 的接口定义 |
| 性能不达标 | 在案例中尝试折中方案（如修订链合并），记录结论 |
| 假设根本不成立 | 记录"假设证伪"，调整方案方向（如从 append-only 回退到锁模型） |
| 边界场景暴露新问题 | 记录到 `03-地基级改造方案.md` 的待决策问题中 |

## 九、不做什么

- 不写生产代码（只写测试 + 最小实现用于验证）
- 不改动现有代码（验证在 `src/session-v2/` 隔离目录内进行）
- 不依赖 feature flag（验证代码独立运行，不影响主流程）
- 不追求 100% 覆盖率（只验证关键假设，不写无关测试）
- 不着急实施——等 5 个案例全部验证通过后再进入正式实施阶段
