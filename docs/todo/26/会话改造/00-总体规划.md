# AI 会话体系重构规划

> 状态：规划中，暂不实施
> 创建：2026-09-27
> 前置分析：见同目录 `01-根因分析.md`

## 一、为什么需要重构

当前会话体系存在 6 个跨设备并发场景下的根因缺陷，已确认为消息丢失/中断的直接原因：

| # | 根因 | 后果 | 严重度 |
|---|---|---|---|
| 1 | JSONL 并发写无文件锁 | 覆写吞追加 → 消息永久丢失 | 致命 |
| 2 | conversationId 反向索引重启丢失 | 孤儿会话 → 消息分裂 | 严重 |
| 3 | streaming 状态跨设备不可靠 | 误中断 / 卡死 | 高 |
| 4 | LRU 驱逐 + 无条件自动创建 | 会话分裂 → 消息断裂 | 高 |
| 5 | persistedSeq 水位跨设备不协调 | seq 冲突 → 重复/错序 | 中 |
| 6 | resume gap 全量覆盖非原子 | 恢复期间新事件丢失 | 中 |

根本矛盾：系统在前端内存态维护了会话状态（SessionStoreManager + persistedSeq + conversationIdToStoreId + LRU），试图支撑跨设备并发实时协作。前端内存状态跨设备天然不可见、不可靠。

## 三、复审：前一版方案的缺陷

前一版方案（8 模块 + 6 轮验证）存在的问题：

### 缺陷 1：模块拆分粒度过细，地基不稳

前一版上来就拆 8 个 Provider interface，每个都要适配器，导致：
- 第一轮要写 8 个 interface + 8 个适配器 + 注册中心，工作量大但零业务价值
- interface 设计在没写新实现前无法验证，很可能"猜错接口"
- 8 个模块之间有隐含依赖（SessionLifecycle 依赖 SessionStore 和 StreamingState），先写谁后写谁会导致循环

**修正**：地基应该是最底层的、最稳定的、不会变的那个接口。不是一上来就拆全部模块，而是找到"一个足够小的内核"。

### 缺陷 2：在前端内存态上做适配，治标不治本

前一版的适配器模式是：新 Provider 包装旧实现，旧实现仍是前端内存态。根本问题（前端内存跨设备不可见）没解决，只是换了个壳。

**修正**：地基必须直接解决"状态在哪里"的问题。不是"包装旧前端状态"，而是"把状态搬到后端"。

### 缺陷 3：没有定义"消息"的权威模型

前一版定义了 8 个 Provider 的操作接口，但没有定义最基本的数据模型：一条消息的全生命周期是什么？谁拥有写入权？版本怎么管？

**修正**：地基必须从"消息的权威模型"开始。先定义清楚"一条消息从产生到持久化到跨设备传播"的完整状态机，再谈模块拆分。

### 缺陷 4：验证策略过于依赖 feature flag 灰度

前一版每轮都靠 feature flag 在新旧实现间切换。但旧实现和新实现共享同一个后端 JSONL 文件，切换时数据格式可能不兼容。

**修正**：验证策略应分层：先验证数据层（新存储格式独立测试），再验证逻辑层（新状态机独立测试），最后才整合适端到端测试。

## 四、修正后的方案：从地基开始

### 核心思路

不拆 8 个模块，而是定义 **1 个内核接口 + 3 个边界**。

```
         ┌──────────────────────────────────────────────────────┐
         │                  UI / Hooks 层                        │
         │            （不替换，通过内核接口访问）                  │
         └───────────────────────┬──────────────────────────────┘
                                 │
         ┌───────────────────────┴──────────────────────────────┐
         │              SessionKernel（内核接口）                  │
         │                                                      │
         │  defineMessage()     一条消息的权威生命周期            │
         │  defineSession()     一个会话的状态机                 │
         │  defineSync()        跨设备同步的协议                  │
         │                                                      │
         │  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐  │
         │  │  Message    │  │   Session    │  │     Sync     │  │
         │  │  Model      │  │   State      │  │   Protocol   │  │
         │  │  (数据)     │  │  Machine     │  │  (一致性)    │  │
         │  └─────────────┘  └──────────────┘  └──────────────┘  │
         │                                                      │
         │  三条边界线：                                          │
         │  边界 A: 前端 ←→ 后端（状态权威在哪）                  │
         │  边界 B: 持久化 ←→ 内存（数据何时落盘）                │
         │  边界 C: 单设备 ←→ 多设备（何时同步）                  │
         └──────────────────────────────────────────────────────┘
                                 │
         ┌───────────────────────┴──────────────────────────────┐
         │            Transport 层（已有，不替换）                │
         └───────────────────────┬──────────────────────────────┘
                                 │
         ┌───────────────────────┴──────────────────────────────┐
         │       Rust 后端（已有，增量扩展命令）                  │
         └──────────────────────────────────────────────────────┘
```

### 地基的第一块砖：Message Model

定义消息的完整生命周期和权威归属，这是整个系统最不会变的东西：

```
消息生命周期：

  [drafted]     前端创建，尚未发送
      │
      ▼ sendMessage()
  [sending]     前端调 aiChatDispatch，等待后端确认
      │
      ▼ 后端返回 conversationId + clientMessageId 透传
  [active]      后端已接收，进入 AI 处理流
      │         ← 此时后端是权威源
      │  ┌──────┤
      │  │      │
      │  ▼      ▼
      │ [streaming]  AI 正在流式输出（delta 事件）
      │  │
      │  ▼ session_end
      │ [settled]    AI 回复完成，消息定稿
      │
      ▼ saveDialog() / appendMessages()
  [persisted]   已落盘，后端持久化为权威
      │
      │  ← 其他设备可从此处恢复
      │
      ▼ restoreFromHistory()
  [restored]    从磁盘恢复到另一设备前端
```

关键设计决策：
- **[active] 和 [persisted] 阶段，后端是权威源**。前端只有快照。
- **[drafted] 和 [sending] 阶段，前端是权威源**。后端尚未确认。
- **跨设备同步只发生在 [active] 和 [persisted] 阶段**，通过事件流 + 快照拉取。
- **消息 ID = clientMessageId**，由最初创建的设备生成，全局唯一，后端透传不修改。

### 地基的第二块砖：Session State Machine

定义会话的状态机和权威归属：

```
会话状态（后端权威）：

  [none]        会话不存在
      │ createSession()
      ▼
  [idle]        会话已创建，无 AI 运行
      │ sendMessage() / continueChat()
      ▼
  [running]     AI 正在处理（streaming）
      │         ← 后端权威，前端只能读不能写 isStreaming
      │  ┌──────┤
      │  │      │
      │  ▼      ▼
      │ [error]  [completed]
      │             │
      │             ▼
      └──────── [idle]（回到空闲，可继续发消息）
```

关键设计决策：
- **isStreaming 由后端 [running] 状态推导**，前端不自行维护。
- **前端每次操作前查询后端真实状态**，不信任本地 isStreaming。
- **两个设备同时操作同一会话**：后端用 conversationId 排他锁，只允许一个 start/continue。
- **[running] 状态下的中断**：任何设备可请求中断，后端确认后广播 session_end。

### 地基的第三块砖：Sync Protocol

定义跨设备同步的一致性协议：

```
同步协议（3 层）：

  层 1: 事件流（实时）
  - 后端 EventBroadcaster 已有 seq + 重放缓冲
  - 增量事件（token/tool_call/...）按 seq 推送
  - 断线后 resume 补发

  层 2: 快照拉取（按需）
  - 后端新增 get_session_snapshot 命令
  - 返回会话的完整状态（消息列表 + running 状态 + conversationId）
  - 用于：断线 gap 恢复、页面重载恢复、新设备首次查看

  层 3: 持久化（落地）
  - 后端 SQLite 作为持久化权威
  - 每条消息按 messageId 幂等写入
  - CAS 乐观锁防并发覆写
  - 消息按 (conversationId, seq) 全局有序
```

关键设计决策：
- **层 1 不变**：已有 EventBroadcaster 足够，只是 gap 时的兜底改为层 2。
- **层 2 新增**：取代当前的 `setMessagesFromHistory` 全量覆盖，改为"快照合并"——拉后端快照 → diff 本地 → 只追加缺失消息。
- **层 3 重写**：废弃前端 JSONL 读写（dialogStorageService），统一由后端 SQLite 管理。前端不再直接写文件。

### 三个边界的设计原则

**边界 A：前端 ←→ 后端（状态权威）**

| 状态 | 权威在哪 | 前端角色 |
|---|---|---|
| 会话是否存在 | 后端 | 查询 |
| 会话是否 running | 后端 | 查询 + 监听推送 |
| 消息列表（active 阶段） | 后端事件流 | 追加（只增不删不覆盖） |
| 消息列表（persisted 阶段） | 后端 SQLite | 查询 |
| 会话元数据 | 后端 SQLite | 查询 + 更新 |
| 输入草稿 | 前端 | 纯本地 |

**边界 B：持久化 ←→ 内存（何时落盘）**

| 操作 | 当前 | 重构后 |
|---|---|---|
| 消息完成 | 前端 saveDialog → JSONL | 后端 session_end 触发自动写入 SQLite |
| 增量追加 | 前端 appendConversationMessages | 后端实时写入（事件 → DB） |
| 历史恢复 | 前端读 JSONL | 前端 invoke 后端查询 SQLite |
| 删除会话 | 前端调后端 dialog_delete | 前端调后端（不变） |

核心变化：**前端不再写文件**。所有持久化由后端在 session_end / 消息完成时自动完成。

**边界 C：单设备 ←→ 多设备（何时同步）**

| 场景 | 同步方式 |
|---|---|
| A 发消息，B 看到回复 | 事件流（层 1） |
| A 发消息时 B 离线 | B 回来后快照拉取（层 2） |
| A/B 同时给同一会话发消息 | 后端排他锁，B 的请求排队等待 |
| 页面重载 | 快照拉取（层 2） |
| 断线 gap | 快照合并（层 2，非全量覆盖） |

### 内核接口 SessionKernel

不拆 8 个模块，只定义一个内核接口。新实现只需实现这个接口：

```typescript
// 这个接口是最不会变的。先定义它，新实现照着写。

interface SessionKernel {
  // ===== 消息生命周期 =====
  // 发送消息：drafted → sending → active
  sendMessage(sessionId: string, message: SendMessageInput): Promise<SendResult>
  // 继续会话（权限授权/回答问题后）
  continueChat(sessionId: string, prompt: string, opts?: ContinueOptions): Promise<void>
  // 中断（任何设备可调用，后端确认后广播）
  interrupt(sessionId: string): Promise<void>
  // 重新生成
  regenerate(sessionId: string, assistantMessageId: string): Promise<void>
  // 编辑重发
  editAndResend(sessionId: string, userMessageId: string, newContent: string): Promise<void>

  // ===== 会话管理 =====
  createSession(opts: CreateSessionOptions): string  // 前端生成 ID
  deleteSession(sessionId: string): Promise<void>
  switchSession(sessionId: string): void
  getActiveSessionId(): string | null
  getSessionMetadata(sessionId: string): SessionMetadata | null
  listSessions(): SessionMetadata[]

  // ===== 状态查询（后端权威） =====
  // 查询会话真实状态（running/idle/error）
  getSessionState(sessionId: string): Promise<SessionState>
  // 获取会话快照（消息列表 + running 状态 + conversationId）
  getSessionSnapshot(sessionId: string): Promise<SessionSnapshot>
  // 获取消息列表（从快照或恢复）
  getMessages(sessionId: string): ChatMessage[]

  // ===== 事件处理 =====
  // 后端事件路由到此方法，内核内部分发
  handleEvent(event: AIEvent): void
  // 订阅会话状态变化
  subscribe(sessionId: string, handler: StateChangeHandler): () => void

  // ===== 恢复 =====
  // 从历史恢复（拉后端快照 → 建会话 → 加载消息）
  restoreFromHistory(historyId: string): Promise<string>
  // 断线重连后恢复（快照合并，非全量覆盖）
  resyncSession(sessionId: string): Promise<void>
}
```

关键点：
- `sendMessage` / `continueChat` / `interrupt` 覆盖了全景图中全部 6 类触发点
- `getSessionState` 取代了前端自行维护 isStreaming
- `getSessionSnapshot` 取代了 setMessagesFromHistory 全量覆盖
- `handleEvent` 统一事件入口，内核内部路由（取代 eventRouter + dispatchEvent 双层路由）

### 与现有插件系统的关系

Polaris 已有 `TransportAdapter`（transport 层）、`DialogBackend`（存储层）、`AIEngine`（引擎层）三个抽象。SessionKernel 不取代它们，而是在它们之上：

```
已有抽象（不替换）：
  TransportAdapter    — 通信层抽象（Tauri IPC / HTTP+WS）
  AIEngine             — 引擎层抽象（Claude Code / Simple AI / 插件引擎）
  EventBus             — 全局事件广播（调试面板等）

新增抽象（替换）：
  SessionKernel        — 会话状态机 + 消息生命周期 + 跨设备同步
    ├── 内部使用 TransportAdapter 通信
    ├── 内部使用 EventBus 广播
    └── 后端新增 SQLite 持久化 + 快照命令
```

## 八、不做什么

- 不拆 8 个独立 Provider interface（过度抽象，地基不稳）
- 不用 feature flag 在业务逻辑层灰度切换（数据格式不兼容风险）
- 不在前端做持久化（所有写操作收到后端）
- 不自行维护 isStreaming（查询后端）
- 不保留 LRU 驱逐 + 自动创建孤儿会话的逻辑
- 不保留 setMessagesFromHistory 的全量覆盖模式
- 不着急实施——等接口设计经过多轮讨论确认后再动手
