# AI 会话体系根因分析

> 状态：已完成
> 创建：2026-09-27

## 一、分析范围

对 Polaris 项目 AI 会话体系的管理、存储、多设备共享三条链路做全量代码走查，定位跨设备并发场景下消息丢失/中断的根因。


## 三、存储机制

### 存储后端三级降级

| 后端 | 路径 | 跨设备共享 | 适用场景 |
|---|---|---|---|
| RemoteBackend | `<DataRoot>/dialogs/*.jsonl` | 是 | 桌面/移动 Web |
| OPFSBackend | 浏览器 OPFS | 否 | 纯静态 Web 离线 |
| LocalStorageBackend | localStorage | 否 | 测试/极端兜底 |

### JSONL 文件格式

每个会话 = 一个 `.jsonl` 文件：
- 第 1 行: DialogMeta (externalId, engineId, title, workspacePath, tokenUsage)
- 第 2+ 行: DialogMessageLine (seq, 完整 ChatMessage)

### SQLite 索引

`<DataRoot>/dialogs/index.db`：
- sessions 表: self + claude-native + plugin-native 统一成行
- FTS5 全文搜索: trigram 分词
- 可丢弃可重建

## 四、多设备同步机制

### 实时事件同步

EventBroadcaster → WebSocket → 前端 eventHandler

- 每条事件分配单调递增 seq
- 环形重放缓冲（2000 条 / 8MB）
- 断线重连发 resume 请求，补发 seq > lastSeq 的事件
- gap = 缓冲已淘汰，客户端走全量恢复

### user_message 多设备同步

- A 设备发消息 → 后端广播 user_message → B 设备追加到 messages
- clientMessageId 幂等去重：A 本机已有同 ID 消息 → 跳过

### 断线重连

- 指数退避重连（1s → 30s，最多 50 次）
- 唤醒立即重连（visibilitychange/online/focus）
- 客户端 25s ping + 服务端 30s ping
- 存活探测（5s 无响应强关半开连接）

## 五、根因分析

### 根因 1：JSONL 文件并发写无跨设备互斥（致命）

三条写入路径共存，无文件锁：

| 路径 | 代码位置 | 操作 |
|---|---|---|
| 整体覆写 | dialog_write_inner (dialog_storage.rs:138) | write tmp → remove old → rename |
| 增量追加 | dialog_append_inner (dialog_storage.rs:162) | OpenOptions::new().append(true) |
| 分页读 | dialog_read_page_inner (dialog_storage.rs:250) | 全量逐行扫描 |

致命竞态场景 — 覆写吞追加：

```
设备A session_end → saveConversation:
  1. 读旧文件（含 M1~M5）
  2. 合并内存消息（M1~M6）
  3. 写 tmp → rename 覆写

设备B session_start → appendConversationMessages:
  X. 在步骤 1→3 之间追加 M7 到旧文件

设备A 步骤 3: rename 覆写
结果: M7 永久丢失
```

enqueuePersist（service.ts:63）的 per-file 串行队列只在前端内存有效，跨设备无互斥。Rust 后端 dialog_write_inner 和 dialog_append_inner 都没有 flock。

### 根因 2：conversationId 反向索引重启丢失 → 孤儿会话

conversationIdToStoreId 是纯内存 Map（sessionStoreManager.ts:145），页面重载后丢失。

竞态场景：
```
设备A: 创建会话 → 后端分配 C1 → 注册 C1→S1
设备A: 页面重载 → conversationIdToStoreId 清空
后端续传事件 { sessionId: C1 } → dispatchEvent 找不到 store
  → 反向索引 miss → 自动创建孤儿会话 S2
  → 原有消息在 S1，新事件进入 S2 → 会话分裂
```

webReconnectResync.ts:107 的 registerConversationId 只在用户主动点击刷新时重注册。

### 根因 3：streaming 状态跨设备不可靠 → 中断/卡死

isStreaming 是纯前端状态，后端事件是唯一同步源。

场景 A — 设备 B 误中断：
```
设备A: 发送消息 → session_start → isStreaming=true
设备B: 收到 session_start → isStreaming=true
设备B: 用户点中断 → interrupt() → 后端杀死 AI 进程
设备A: 收到 session_end(reason=interrupted) → 回复被截断
```

场景 B — streaming 状态不同步导致卡死：
```
设备A: 发送消息 → isStreaming=true
设备A: 网络断开 → 错过 session_end → 永远 isStreaming=true
  → 5s 中断超时兜底只对本机主动中断生效
  → 不是本机发起的 session_end 不触发超时
  → UI 卡在转圈
```

场景 C — resume gap 恢复覆盖期间新事件丢失：
```
resyncSession:
  1. 查后端存活
  2. 重拉历史 → setMessagesFromHistory 全量替换 messages
  3. 校正 isStreaming

步骤 2→3 之间后端推送新 delta → 被全量覆盖丢失
```

### 根因 4：LRU 驱逐 + 自动创建 → 会话分裂

evictIdleSessions（sessionStoreManager.ts:56）驱逐非活跃会话。

```
设备A: 7 个非活跃会话 → LRU 驱逐 S1
  → S1 的 store 被 dispose
后端: 继续向 S1 推送事件 → dispatchEvent
  → 找不到 store → 反向索引 miss → 自动创建新会话 S_new
  → S1 的历史消息不在 S_new 中 → 消息断裂

设备B: 仍在看 S1（B 没有驱逐）→ A 和 B 看到完全不同的内容
```

驱逐后的自动创建（sessionStoreManager.ts:714-738）是无条件的。

### 根因 5：persistedSeq 水位跨设备不可靠 → 重复写入/丢失

persistedSeq 是前端内存态，记录已落盘的消息条数。

```
设备A: 恢复 → persistedSeq = 5
设备A: M6 完成 → append M6 → persistedSeq=6
设备B: 同时恢复 → persistedSeq = 5（不知道 A 已追加 M6）
设备B: M7 完成 → append M7 at seq=5
  → M6 和 M7 的 seq 冲突
  → dialog_read_page_inner 按 seq 排序时重复/错序
```

### 根因 6：resume gap 全量覆盖非原子

resyncSession（webReconnectResync.ts:114）的 setMessagesFromHistory 直接 set({ messages })，是全量替换。恢复期间新事件被覆盖丢失。

## 六、根本矛盾

系统在前端内存态维护了会话状态（SessionStoreManager + persistedSeq + conversationIdToStoreId + LRU），试图支撑跨设备并发实时协作。前端内存状态跨设备天然不可见、不可靠，每一条优化路径（增量追加、LRU 驱逐、自动创建）在跨设备并发下都会变成数据丢失的入口。
