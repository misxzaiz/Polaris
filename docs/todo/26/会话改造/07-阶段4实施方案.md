## 一、阶段定位

阶段 4 是 session-v2 重构的**分水岭**：前三个阶段（0~3）全部是"影子运行"——V2 内核与现有业务路径并存，零改动现有代码。阶段 4 开始，要把 V2 内核**真正接进现有业务链路**：

- 根因 3（streaming 跨设备不可靠）→ 后端权威状态取代前端 isStreaming
- 根因 4（LRU 驱逐 + 自动创建孤儿会话）→ 会话注册表持久化取代内存 Map
- 根因 5（persistedSeq 跨设备不协调）→ 后端 seq 权威取代前端水位
- 根因 6（resume gap 全量覆盖非原子）→ 快照合并/对账取代 setMessagesFromHistory

**风险声明**：这是六根因中剩余 4 个的消除点，也是 8 个 isStreaming 消费方 + 6 类触发点的改造点。一旦开始，就不再是"影子运行"，会真实影响主流程。因此本方案强调**分批切换 + 可回滚 + 双路径并存**。

---

## 二、目标

### 2.1 业务目标

1. **消除前端 isStreaming 作为状态源**：8 个消费方全部改为查询后端状态（`getSessionState`），前端不再自行维护流式状态。
2. **消除前端 persistedSeq 水位**：落盘水位由后端事件日志 seq 权威取代，前端不再计算"已落盘条数"。
3. **消除前端 conversationIdToStoreId 内存 Map**：由后端 Session Registry（`session_records` 表）取代，重启后反向索引不丢失。
4. **消除 LRU 驱逐导致的孤儿会话**：会话不再被无条件自动创建，改为从注册表恢复。
5. **resume gap 恢复改为快照合并**：断线重连不再全量覆盖，改为 reconcile 差异补齐。
6. **V2SessionKernel 成为唯一入口**：6 类触发点全部经由能力接口走 V2 内核，Legacy 桥接退役。

### 2.2 非目标

- 不改动后端 `router_dispatch_stream` / `ai_chat_capability` 的既有协议（只在其上附加 session_events 写入）
- 不改动旧 JSONL 存储（`dialogs/*.jsonl` 保留，作为历史只读）
- 不迁移历史会话数据（新会话走 V2，旧会话仍可从 JSONL 恢复）
- 不引入新的框架/库

## 四、开放问题（实施前必须决策）

### O1：流式期间消息不可变 vs 可变（03 文档待决策 #1）

**现状**：`eventHandler` 在流式期间实时修改消息的 blocks（追加 tool_call、更新 thinking、累积 text）。若消息不可变，这些实时修改需改为"追加修订"，每秒几十个 delta 会产生大量修订记录。

**已验证**：案例 2 证明 100 次 revise 仅 1.8ms（性能无问题），但**渲染侧**：现有 `ConversationStore` 直接 `set({ messages })` 触发 React 重渲染，改成修订链需要消息版本追踪 + 合并渲染。

**候选方案**：
- **方案 A（推荐）**：流式期间消息**可变**（沿用现有 eventHandler 逻辑，写后端时以"最新版本"落库），session_end 后**冻结**为不可变（不再修改）。即"可变窗口 + 冻结"折中。
- **方案 B**：全程不可变，流式 delta 全部为修订记录。渲染侧需新增"取最新版本"逻辑。
- **方案 C**：流式期间不写后端（仅内存），session_end 一次性落盘。最简单但断线恢复期间会丢中间状态。

**倾向**：A。理由：现有 UI 渲染链路零改动，风险最小；冻结后天然满足"消息不可变"的跨设备一致性（案例 1/2 已验证 append-only 幂等）。

### O2：崩溃后谁补插 session_end

案例 3 已验证"后端启动时扫描无配对 session_start 补插 end"，但 03 文档缺陷 3 指出后端本身也会崩溃。需要双层兜底：

**候选方案**：
- 方案 A：后端启动扫描补插（已验证）
- 方案 B：查询时加超时判断（session_start 后 N 秒无新事件视为崩溃）
- **倾向**：A + B 组合——启动补插兜底 + 查询时超时兜底（对"后端长跑期间会话卡死"更有效）。

### O3：对账频率

reconcile 是断线后调一次，还是定期心跳？

**倾向**：断线恢复 + 页面重载 + 新设备首次查看时调用；不做定期心跳（避免后端负载，案例 4 已验证 0.93ms/1000 条，即使定期成本也可控，但初期从简）。

### O4：8 个消费方改造的兼容策略

**现状**：8 个消费方从 `store.isStreaming` 读状态。V2 改造后 `getSessionState` 是异步的。

**倾向**：消费方改为订阅 `kernel.subscribe(sessionId, handler)`（能力 3 已提供），在 handler 里拿 `SessionState`。对仍用 `store.isStreaming` 的临时兼容层保留一个只读投影（从后端状态推导），但不作为状态源。

### O5：双路径并存期的一致性问题

阶段 4 期间 Legacy 与 V2 影子并存，同一会话可能有两条状态路径。需要明确：
- 写路径统一走 V2（后端权威）
- 读路径消费方走 V2
- Legacy 只保留为"未改造消费方的兜底"，不参与写

## 五、实施方案

### 5.1 总体思路：分批切换，每批可独立验证可回滚

```
批次 1：V2 内核实现 + 事件日志附加写入（影子）       ← 后端权威链路就绪
批次 2：8 个消费方改造（读路径切到 V2）              ← 消除 isStreaming 作为状态源
批次 3：6 类触发点接入 V2 内核（写路径切到 V2）      ← 消除前端状态维护
批次 4：注册表重启恢复 + resume 快照合并             ← 消除根因 2/4/6
批次 5：Legacy 桥接退役 + 清理                       ← 收敛
```

每批次独立提交、独立测试、可回滚（保留前一版本代码，feature 开关切换）。

### 5.5 批次 4：后端 dispatch 链路附加写入 + 注册表恢复

**Rust 侧**（`src-tauri/src/services/session_state.rs` / `src-tauri/src/ai/engine/`）：

1. `router_dispatch_stream` start/continue 时：`session_event_append(session_start)`（带 deviceId、conversationId）
2. `session_end` 时：`session_event_append(session_end)`（带 reason）
3. `interrupt` 时：`session_event_append(session_end, reason=aborted)`
4. `ai_chat_capability` 的 dispatch 入口：`session_request_start` 排他检查

**前端恢复**：

```
页面加载 → getKernel() → listSessions()（注册表）→ 重建 conversationIdToStoreId
         → 对活跃会话 resyncSession()（reconcile 快照合并）
```

## 八、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 消费方改造引入回归 | 主流程中断 | 每批次独立提交 + 全量 vitest + 手工冒烟；先改读路径后改写路径 |
| 后端事件写入失败 | 状态缺失 | 写入失败仅告警不阻断主流程（事件日志是增强不是前置依赖） |
| 双路径并存期状态漂移 | 显示不一致 | 写路径统一 V2，Legacy 只读兜底 |
| 流式修订策略未决（O1） | 渲染性能/一致性 | 先按方案 A（可变窗口 + 冻结），验证后再评估 B |
| 排他锁接入影响并发体验 | 用户等待 | 拒绝而非排队（阶段 2 已定），前端提示"会话正忙" |
