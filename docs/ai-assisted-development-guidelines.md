# AI 辅助开发规范实践指南

> 适用范围：通用场景（不限语言/框架），同时给出本仓库（Tauri + React/TS 前端 + Rust 后端 + SimpleAI/MCP 生态）的落地映射。
> 编写日期：2026-08-06。版本：v1.0。
> 知识来源：GitHub SDD（Spec-Driven Development）思路、Anthropic Claude Code 最佳实践、ThoughtWorks 技术雷达关于 AI 结对的观点、主流 AI 编码工具（Cursor / Copilot / Claude Code / Codex CLI）的通用推荐流程。受网络限制，本次未能在编写时实时引用线上链接，条目均依据行业共识与工程经验提炼，可在「参考来源」补全后追溯。

---

## 0. 总则：AI 辅助开发的四条铁律

1. **人机责任分层**：AI 负责"生成与检索"，人负责"决策与验收"。任何进入主干的内容，必须经过人类明确确认。
2. **规格先行（Spec-Driven）**：先写清楚要做什么（Spec / AC），再让 AI 实现。没有验收标准的任务不进入实现阶段。
3. **小步快走，可回滚**：AI 生成速度快，但错误也快。每个可独立验证的变更对应一个提交/PR，禁止大而全的合并。
4. **可验证 > 可读 > 优雅**：AI 最容易产出"看起来对"的代码。第一道防线永远是测试和编译，而不是代码风格。

## 1. 技术栈覆盖

### 1.1 前端开发规范

**组件组织**
- 单一职责：一个组件只做一件事。容器组件（取数据/状态）与展示组件（纯渲染）分离。
- 自上而下的数据流：状态上提，事件下传。跨层共享通过 store，而非 props 逐层穿透超过 2 层。
- 文件即边界：一个文件一个默认导出组件，副作用 hook（如数据请求）单独抽文件，便于测试与替换。

**状态管理**
- 三层状态分层：组件局部状态（useState）→ 临近共享（context/zustand slice）→ 全局持久（store + 持久化）。禁止把所有状态塞进单一全局 store。
- 派生数据用 selector，不要在 store 里冗余存储可计算值。
- 异步状态必须含 `pending/success/error/idle` 四态，禁止只用 `loading` 布尔。

**样式方案**
- 优先 CSS 变量 + 语义化类名，避免内联 style 频繁切换（触发重排）。
- 主题相关值走 token（如 `--brand-color`），禁止硬编码色值/圆角（本仓库主题系统有 60+ 处 border-radius 硬编码的教训）。
- 动态主题用"变量注入 + 独立 style 标签"组合，避免对运行时 CSSOM 的大量 patch。

**API 交互模式**
- 统一 client 层：所有网络请求走封装的 client，禁止在组件内裸用 fetch/axios。
- 请求/响应类型由契约生成（OpenAPI / tRPC），而非手写。
- 错误统一拦截：网络错误、鉴权失效、业务码分层处理，组件只关心业务结果。

### 1.2 后端开发规范

**接口设计**
- RESTful 优先；命名用复数名词 + 资源层级。RPC 风格仅用于动作语义强且无状态资源的场景。
- 幂等性优先：写操作尽量可重入（带 idempotency-key 或唯一约束）。
- 分页/过滤/排序统一 query 约定，响应固定结构 `{ data, meta, error }`。

**数据模型**
- 领域模型与传输模型（DTO）分离，禁止把 ORM 实体直接序列化给前端。
- 时间用 UTC 存储、按需转时区；金额用最小单位整数；枚举用命名常量而非魔数。
- 迁移可重入、可回滚，禁止 destructive 迁移直接上生产。

**错误处理**
- 三类错误：校验错误（400）、业务规则错误（422）、系统错误（5xx）。各自的日志级别与暴露给前端的细节不同。
- 错误信息对用户友好、对开发者可定位：携带 traceId，前端可回传。

**日志与监控**
- 结构化日志（JSON），含 traceId/userId/requestId/latency。
- 日志级别分明：INFO 走量、WARN 走问题、ERROR 走告警。禁止把循环里的常规路径打成 ERROR。
- 关键指标埋点：QPS、p99 延迟、错误率、资源占用。

### 1.3 全栈联调规范

**前后端契约**
- 契约是单一事实来源：类型、字段、枚举、错误码都从契约派生，前端不臆造字段。
- 契约变更必须双向 review：后端改字段，前端同步改消费方，否则视为破坏性变更。

**Mock 策略**
- 三层 Mock：开发期（本地 mock server）→ 联调期（真实后端 + 透明 mock 兜底）→ E2E（真实全链路）。
- Mock 数据要有"真实感"：边界值、空集、超长、特殊字符，避免全用 "test"。

**接口版本管理**
- 破坏性变更升版本号（/v2/），非破坏性变更就地扩展。
- 废弃接口打 deprecation 头，给一个迁移周期再下线。

## 2. 全流程规范

每个阶段结构统一：**目标 → 输入 → 流程 → 产出物 → 检查点（含 checklist）**。

### 2.1 需求阶段

**目标**：把模糊想法变成可验收的明确需求。

**输入**：用户/产品口述需求、业务背景、约束条件。

**流程**：
1. AI 辅助起草用户故事（User Story）："作为 X，我想 Y，以便 Z"。
2. 人补充业务背景与边界，AI 据此生成验收标准（AC）。
3. 评审：逐条确认 AC 可观测、可测试、无歧义。
4. 明确范围：做什么、不做什么、延后做什么。

**产出物**：需求卡（含用户故事 + AC + 范围说明 + 非功能约束）。

**检查点 checklist**：
- [ ] 每条 AC 可被测试用例直接覆盖（无"体验更好"这类主观措辞）
- [ ] 范围已写明"本期不做"清单
- [ ] 非功能约束（性能/安全/兼容）已列出
- [ ] 依赖与前置项已识别
- [ ] 需求与现有功能无重复或冲突已确认

### 2.2 测试设计阶段

**目标**：在写实现前，先定义"怎样算对"。

**输入**：需求卡（AC 清单）。

**流程**：
1. 按 AC 反推测试用例：每条 AC 至少 1 个正向 + 1 个边界 + N 个异常。
2. 分类：单元 / 集成 / E2E，明确每条用例归属哪层。
3. 设定覆盖率目标（单元 ≥80% 是常见阈值，非强求 100%）。
4. 识别边界条件：空值、极值、并发、超时、权限、跨时区。

**产出物**：测试用例矩阵（用例编号 ↔ AC ↔ 层级 ↔ 输入/预期）。

**检查点 checklist**：
- [ ] 每条 AC 都有对应测试用例（双向映射表）
- [ ] 边界与异常用例不少于正向用例
- [ ] 测试分层已标注，无"E2E 滥用"（能单元测的不放 E2E）
- [ ] 覆盖率目标已写明，且区分"行覆盖/分支覆盖"
- [ ] 测试数据策略已定（构造、清理、隔离）

### 2.3 开发阶段

**目标**：按规格实现，保证可读、可测、可回滚。

**输入**：需求卡 + 测试用例矩阵 + 技术方案（可选但推荐）。

**流程**：
1. 分支策略：`feat/<scope>`、`fix/<scope>`、`chore/<scope>`，短生命周期。
2. 编码：AI 生成草稿 → 人 review → 跑测试 → 提交。
3. 提交规范：Conventional Commits（`feat:` / `fix:` / `refactor:` / `test:` / `docs:` / `chore:`），一个提交一件事。
4. 代码审查：PR 必须有人类 review，AI 可作为辅助 reviewer 但不作为唯一审查者。
5. 质量门禁：CI 必过（lint / type-check / 单测 / build）方可合并。

**产出物**：可运行代码 + 单元测试 + PR（含变更说明）。

**检查点 checklist**：
- [ ] 分支从最新主干切出，无冗余历史
- [ ] 提交信息符合规范，且每条提交单一职责
- [ ] 单元测试新增/更新，且本地通过
- [ ] AI 生成代码已逐行 review（重点：无幻觉 API、无死代码、无复制粘贴重复）
- [ ] 类型检查/lint/build 全绿
- [ ] 无调试代码（console.log / dbg! / TODO 无 issue）残留
- [ ] 危险操作（删数据/迁移/权限变更）已人工二次确认

### 2.4 测试阶段

**目标**：验证实现满足 AC，且无回归。

**输入**：可运行代码 + 测试用例矩阵。

**流程**：
1. 单元测试：函数级，毫秒级完成。
2. 集成测试：模块级，验证协作与契约。
3. E2E：关键用户路径，覆盖最薄一层。
4. 缺陷管理：每个缺陷记复现步骤、环境、预期/实际。
5. 回归策略：缺陷修复必须带回归测试；发布前跑全量回归。

**产出物**：测试报告（通过率 / 失败清单 / 覆盖率）+ 缺陷清单。

**检查点 checklist**：
- [ ] 三层测试全部执行且有报告
- [ ] 关键用户路径（登录/核心业务/支付类）有 E2E 守护
- [ ] 缺陷分级（Blocker/Major/Minor）并有处理结论
- [ ] 回归测试包含本次修复项 + 相邻高风险项
- [ ] 性能基线（p99 / 内存 / 启动耗时）未劣化
- [ ] 跨端/跨环境验证（本仓库：桌面 Tauri + Web + 移动端）

## 3. 规范条目详解（为什么重要 / 怎么做 / 常见误区）

> 以下条目是高频踩坑点，每条独立可查。

### 3.1 规格先行（Spec-Driven）

- **为什么重要**：AI 没有规格时会"自由发挥"，产出看起来合理但偏离意图的代码，返工成本远高于先写规格。
- **怎么做**：需求阶段产出 Spec（含 AC），实现阶段把 Spec 喂给 AI 作为约束；实现完成后用 AC 逐条验收。
- **常见误区**：把 PRD 当 Spec（PRD 描述"想要什么"，Spec 描述"做成什么样才算对"，二者不同）；AC 写成功能描述而非可测条件。

### 3.2 AI 生成代码的人工审查

- **为什么重要**：AI 会编造不存在的 API（幻觉）、留下未使用的死代码、复制粘贴产生重复块。这些只有人能识别。
- **怎么做**：PR 审查必查三件事——调用的 API 是否真实存在（查文档/源码）、新代码是否被实际调用、重复逻辑是否该抽公共函数。
- **常见误区**：因为"AI 写得快、测试过了"就跳过 review；只看 diff 不跑起来验证关键路径。

### 3.3 小步提交与可回滚

- **为什么重要**：AI 一次生成大段代码，若整体合并后才发现问题，回滚范围大、定位难。
- **怎么做**：把任务拆成可独立验证的小步，每步一个提交；提交粒度 = "能单独通过测试 + 单独解释做了什么"。
- **常见误区**：一个 PR 塞多个功能点（评审与回滚都困难）；为"省提交"把无关重构混进功能提交。

### 3.4 测试先行与分层

- **为什么重要**：AI 写的代码最容易在边界出错；E2E 跑得慢且定位难，滥用会让反馈回路变长。
- **怎么做**：先写/先确认测试用例再实现；能用单元测试覆盖的不放集成，能集成覆盖的不放 E2E；E2E 只守关键路径。
- **常见误区**：追求 100% 行覆盖却忽视分支；E2E 滥测每个按钮，导致一次跑半小时且频繁 flaky。

### 3.5 契约为单一事实来源

- **为什么重要**：前后端各写一份类型，必然漂移；AI 又会加剧（它会按"合理推测"补字段）。
- **怎么做**：从 OpenAPI/Schema 生成前后端类型；契约变更触发双向同步检查。
- **常见误区**：前端手动复制后端类型；后端加字段前端不知道，运行时静默 undefined。

### 3.6 状态与副作用的边界

- **为什么重要**：AI 倾向把状态散落在组件里，导致数据流难追踪、内存泄漏（本仓库曾有 EventBus 历史无上限、highlight Cache 无限增长的真实教训）。
- **怎么做**：状态分层明确；缓存必须有 LRU/TTL 上限；订阅必须在对应生命周期清理。
- **常见误区**：所有状态塞全局 store；缓存无上限（OOM 后才补救）；事件监听只 add 不 remove。

### 3.7 危险操作的人工二次确认

- **为什么重要**：AI 不会为删库、破坏性迁移、权限变更踩刹车。
- **怎么做**：destructive 操作（删数据、drop、force push、生产权限）必须人类显式确认；CI 门禁禁止自动跳过。
- **常见误区**：为图快给 AI 全权代理；把生产凭据交给 AI 执行环境。

### 3.8 可观测性内建

- **为什么重要**：AI 写的代码常缺日志与埋点，出问题后"黑盒"。
- **怎么做**：关键路径埋结构化日志与指标；错误带 traceId；异常分支有 WARN。
- **常见误区**：只在出错时临时加日志；把高频正常路径打成 ERROR 造成告警风暴。

## 4. 团队规模的可选方案

| 维度 | 简单方案（1-3 人 / 个人项目） | 标准方案（5-15 人 / 一般团队） | 最优方案（20+ 人 / 高合规要求） |
|---|---|---|---|
| 需求 | 口述 + Markdown AC | 需求卡 + AC + 评审记录 | 需求卡 + AC + 评审 + 变更控制 + 追溯矩阵 |
| 测试设计 | AC 反推用例，文档化 | 测试矩阵 + 覆盖率目标 + 分层 | 矩阵 + 覆盖率 + 变异测试 + 性能基线 |
| 开发 | Conventional Commits + 单分支 | 分支策略 + PR review + CI 门禁 | 分支策略 + 双人 review + 多级门禁 + 人工+AI 双审 |
| 测试 | 单元 + 手工 E2E | 三层分层 + 缺陷管理 | 三层 + 回归套件 + 缺陷分析 + SLO 守护 |
| 契约 | 手写共享类型 | OpenAPI 生成类型 + 变更检查 | 契约 + schema registry + 破坏性变更自动检测 |
| AI 审查 | 人工逐行 review | 人工 + AI 辅助 reviewer | 人工 + AI 双审 + 安全扫描 + 依赖审计 |
| 文档 | 代码即文档 | ADR + PR 说明 | ADR + 变更日志 + 外部规格文档 |

> 选择建议：从标准方案起步，按团队实际痛点向上加配。最优方案的成本只有在规模或合规要求到位时才划算。

> 把通用规范映射到当前项目，便于直接执行。非通用部分，供其他项目参考"如何本地化"。

| 规范条目 | 本仓库落地 |
|---|---|
| 规格先行 | 已有 `sdd-integration-plan.md`、`/spec` 命令、`spec-developer` 专家；需求卡写入 `docs/specs/` |

| AI 审查 | 本仓库多处用 workflow 做对抗式验证（hard-problem-assault），可作为 AI 辅助 reviewer 的范式 |
