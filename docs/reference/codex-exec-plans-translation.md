## 一、概述：使用 PLANS.md 进行多小时的复杂问题求解

Codex 和 `gpt-5.2-codex` 模型（推荐）可用于实现那些需要大量时间进行研究、设计和实现的复杂任务。本文描述的方法是一种引导模型实现这些任务、并引导其成功完成项目的有效方式。

这些计划是详尽的设计文档，也是"活文档"。作为 Codex 的用户，你可以在 Codex 开始漫长的实现过程之前，通过这些文档来验证 Codex 将要采取的方法。

下面这份 `PLANS.md` 与一份曾让 Codex 从**单条 prompt 出发持续工作超过七小时**的文档非常相似。

使用方式：先更新 `AGENTS.md` 描述何时使用 `PLANS.md`，然后将 `PLANS.md` 文件添加到仓库中。

---

## 二、AGENTS.md

[AGENTS.md](https://github.com/openai/agents.md) 是一种简单的格式，用于引导 Codex 等编码 agent。我们定义一个用户可用的简写术语，以及一条何时使用规划文档的简单规则。

这里我们将规划文档称为 **"ExecPlan"**。注意这是一个任意术语，Codex 并未针对其训练过。这个简写可用于在 prompt 中引导 Codex 指向特定的计划定义。

一个 `AGENTS.md` 中用于指示 agent 何时使用计划的示例：

```md
# ExecPlans
When writing complex features or significant refactors,
use an ExecPlan (as described in .agent/PLANS.md)
from design to implementation.
```

## 三、PLANS.md 完整规范

### 3.1 引言

Codex 执行计划（ExecPlan）是一种设计文档，编码 agent 可以遵循它来交付一个可工作的特性或系统变更。

**对待读者如同该仓库的完全新手**：他们只有当前工作目录树和你提供的唯一一份 ExecPlan 文件。没有 prior plan 的记忆，也没有任何外部上下文。

---

### 3.2 如何使用 ExecPlans 和 PLANS.md

**撰写 ExecPlan 时：**

- 严格遵循 PLANS.md，逐字执行
- 如果 PLANS.md 不在上下文中，通过重新阅读整份 PLANS.md 来刷新记忆
- 彻底阅读（和反复阅读）源材料，以产出准确的规格
- 创建 spec 时，从骨架开始，在研究中逐步充实

**实施 ExecPlan 时：**

- 不要询问用户"下一步做什么"；直接推进到下一里程碑
- 保持所有章节最新，在每一个停靠点添加或拆分列表条目，明确陈述已取得的进展和下一步
- 自主裁决歧义，频繁 commit
- 讨论 ExecPlan 时，在 spec 中记录决策日志供后人参考；对规格的任何修改原因应清晰无疑
- ExecPlans 是活文档，应始终能够**仅凭该 ExecPlan 重启**，无需其他任何工作

**研究阶段：**

- 对于需求具有挑战性或存在重大未知因素的设计，使用里程碑来实现概念验证（PoC）、"玩具实现"等，以验证用户提议的可行性
- 通过查找或获取库的源代码来阅读它们，深入研究，并通过原型引导更完整的实现

---

### 3.3 不可协商的要求

| # | 要求 | 说明 |
|---|------|------|
| 1 | **完全自包含** | 文档当前形式包含新手成功所需的所有知识和指令 |
| 2 | **活文档** | 随着进展、发现、设计决策的确定而持续修订，每次修订后仍须完全自包含 |
| 3 | **新手可实施** | 必须让一个完全新手能在不预先了解该仓库的情况下端到端实现该特性 |
| 4 | **可验证的行为** | 必须产出可演示的工作行为，不仅仅是"符合定义的代码变更" |
| 5 | **术语即定义** | 每个专业术语必须用平实语言定义，否则不使用 |

具体指引：

- **目的和意图优先**。用几句话解释为什么这个工作从用户视角看很重要——用户在此变更后能做什么以前不能做的事，以及如何看到它在工作。
- **引导读者完成精确步骤**：需要编辑什么、运行什么、应该观察到什么。
- 执行你计划的 agent 可以列出文件、读取文件、搜索、运行项目、运行测试。它**不知道任何 prior context**，也**不能从早期里程碑推断你的意图**。
- **重复你依赖的任何假设**。
- **不要指向外部博客或文档**；如果需要知识，用你自己的话嵌入到计划中。
- 如果 ExecPlan 建立在先前的 ExecPlan 之上且该文件已检入，通过引用合并。如果未检入，则必须包含该计划的所有相关上下文。

---

### 3.4 格式要求

格式和外壳简单而严格：

- 每个 ExecPlan 必须是**单个围栏代码块**，标记为 `md`，以三个反引号开始和结束
- **不要在内部嵌套额外的三反引号**；需要展示命令、转录、diff 或代码时，使用该单围栏内的缩进块呈现
- 使用缩进而不是代码围栏，以避免过早关闭 ExecPlan 的代码围栏
- 每个标题后使用两个换行，使用 `#`、`##` 等标记，正确使用有序和无序列表语法

**写入 `.md` 文件且文件内容仅为该 ExecPlan 时**，省略外层三反引号，直接使用平实散文编写。

**句子优先于列表**。避免清单、表格和长枚举，除非简洁会损害含义。清单**仅允许在 `Progress` 部分使用**，且在此处是强制性的。叙述性部分必须保持散文优先。

---

### 3.5 编写指南

#### 自包含与平实语言至上

- 如果引入一个非普通英语短语（如 "daemon"、"middleware"、"RPC gateway"、"filter graph"），立即定义它，并提醒读者它在仓库中如何体现（例如，命名文件或命令）
- 不要说"如前定义"或"根据架构文档"——即使需要重复，也要在此处包含所需解释

#### 避免常见失败模式

- 不要依赖未定义的术语
- 不要将特性描述得过于狭窄，以至于结果代码能编译但没有实际意义
- 不要将关键决策外包给读者——存在歧义时，在计划中自行裁决并解释选择该路径的原因
- 宁可**过度解释用户可见效果**，也不要过度说明具体的实现细节

#### 锚定于可观察的结果

- 说明用户实施后能做什么、要运行的命令、应看到的输出
- 验收应以**人类可验证的行为**来表述（如"启动服务器后，访问 `http://localhost:8080/health` 返回 HTTP 200，响应体为 OK"），而不是内部属性（如"添加了 HealthCheck 结构体"）
- 如果是内部变更，解释其影响如何被演示（例如，通过运行前后失败的测试，或展示使用新行为的场景）

#### 显式指定仓库上下文

- 使用仓库相对路径命名文件，精确定位函数和模块，描述新文件应创建的位置
- 如果涉及多个区域，包含一段简短的方向说明，解释这些部分如何组合，以便新手能自信导航
- 运行命令时，展示工作目录和精确的命令行
- 当结果依赖环境时，说明假设并提供合理的替代方案

#### 幂等与安全

- 编写步骤使其可多次运行而不会造成损害或漂移
- 如果某步骤可能中途失败，包含如何重试或适配
- 如果需要迁移或破坏性操作，说明备份或安全回退方案
- 优先选择**可增量验证的添加性变更**

#### 验证不可选

- 包含运行测试、启动系统（如适用）以及观察其完成有用工作的指令
- 描述新特性或能力应包含的全面测试
- 包含预期输出和错误信息，以便新手区分成功与失败
- 尽可能展示如何证明变更的有效性（例如，通过小型端到端场景、CLI 调用或 HTTP 请求/响应记录）
- 说明项目工具链对应的确切测试命令及其结果解读方式

#### 捕获证据

- 当步骤产生终端输出、简短 diff 或日志时，在单围栏块内以缩进示例形式呈现
- 保持简洁，聚焦于证明成功的内容
- 如需包含补丁，优先使用文件级 diff 或小片段，让读者能通过按步骤操作复现，而不是粘贴大段内容

---

### 3.6 里程碑

里程碑是**叙事**，不是官僚流程。如果将工作拆分为里程碑，每个里程碑应包含：

- 一段简短段落描述范围
- 里程碑结束时存在什么之前不存在的东西
- 需要运行的命令
- 预期观察到的验收结果

保持可读性，像故事一样：**目标 → 工作 → 结果 → 证据**。

**Progress 和里程碑是不同的**：里程碑讲述故事，Progress 跟踪颗粒度工作。两者都必须存在。

- 绝不要仅仅为了简洁而缩写里程碑，不要遗漏可能对未来实施至关重要的细节
- 每个里程碑必须**独立可验证**，并逐步实现执行计划的总体目标

---

### 3.7 活文档与设计决策

- ExecPlans 是活文档。做出关键设计决策时，更新计划以记录决策及其背后的思考。**所有决策记录在 `Decision Log` 部分**
- ExecPlans 必须包含并维护以下部分（**不可选**）：`Progress`、`Surprises & Discoveries`、`Decision Log`、`Outcomes & Retrospective`
- 当发现优化器行为、性能权衡、意外 bug 或影响方案选择的反向/解应用语义时，将这些观察捕获到 `Surprises & Discoveries` 部分，附带简短证据片段（测试输出为佳）
- 如果在实现过程中改变方向，在 `Decision Log` 中记录原因，并在 `Progress` 中反映影响。计划是为下一个贡献者提供的指南，也是为你自己的清单
- 在完成主要任务或完整计划时，编写 `Outcomes & Retrospective` 条目，总结已完成的内容、剩余工作以及经验教训

---

### 3.8 原型里程碑与并行实现

**原型里程碑：**

可以——而且通常鼓励——包含明确的原型里程碑，以降低更大变更的风险。例如：
- 向依赖项添加底层操作符以验证可行性
- 在测量优化器效果的同时探索两种组合顺序

要求：
- 保持原型**可添加和可测试**
- 清晰标注范围为"原型"
- 描述如何运行和观察结果
- 说明推广或弃用原型的标准
- 优先使用添加性代码变更，然后通过减法保持测试通过

**并行实现：**

在迁移期间保持适配器与旧路径并存是可以的，当它们能降低风险或使测试在大型迁移期间持续通过时。描述如何确保两者的一致性，以及最终清理旧路径的计划。

## 四、与 Polaris SDD 的核心差异对比

| 维度 | OpenAI ExecPlan | Polaris SDD (ADR 0007) |
|------|----------------|------------------------|
| **定位** | 一条 prompt 驱动的 agent 执行计划（L3 实施计划） | 三层体系（宪法→规格→计划），更偏重需求管理 |
| **自包含要求** | 极端严格：仅凭一份文件 + 当前代码树，新手可端到端实现 | 有上下文理解，假设 Agent 具备项目背景知识 |
| **格式约束** | 单个 md 代码块，不嵌套三反引号，散文优先，只有 Progress 用清单 | 标准 Markdown 文档，自由使用表格/列表/代码块 |
| **EARS 语法** | 未引入 | 强制使用 EARS 五模式（Ubiquitous/Event-driven/State-driven/Unwanted/Optional） |
| **必备章节** | Progress、Surprises & Discoveries、Decision Log、Outcomes & Retrospective | Context、Intent、Architecture、Constraints、Acceptance Criteria、Risks、Traceability、Validation Plan、Rollout |
| **生命周期** | 一次性的"写→执行"两阶段，无状态管理 | 完整生命周期：Draft→In Review→Approved→Implemented→Superseded |
| **AGENTS.md 联动** | 核心组件：通过 AGENTS.md 触发 PLANS.md | 无对应机制，通过 `/spec` 命令 + system prompt 协议触发 |
| **原型/并行实现** | 明确鼓励，接地气 | 未在模板中体现 |
| **活文档要求** | 极强：每次修订必须保持自包含、重启可行 | 有状态管理，但未强调"从计划重启"能力的保持 |
| **验证要求** | 可观测行为 > 编译通过，命令级证据捕获 | AC 验证矩阵，但证据粒度较粗 |
| **适用场景** | Codex 单 agent 长时工作（7h+ 单 prompt） | 多 Agent/多工程师协作，统一真实来源 |
