commit 307b841f src/stores/conversationStore/eventHandler.ts 2026-09-10 复核结论：标题误导

user_message 事件消费 — 影响面复核

提交自称「多设备同步」，实际改动的是 claude CLI 引擎的本地渲染行为，且引入会话标题劫持与静默历史截断两条更严重的副作用。

核心结论

这不是一个多设备问题。event_parser.rs:729 无条件把 claude CLI 回流的任何 user-role text 块发成 UserMessageEvent；前端改成消费之后，单台设备本地会话里 Claude Code 自己的内部消息就被渲染成用户气泡。跨设备同步只是同一个 bug 的另一面。

更严重的是它已经落盘。假用户消息经 saveDialog 写进 JSONL，而 buildDialogMetaInput / extractFirstUserText 用 messages.find(m=>m.type==='user') 取会话标题——假消息会劫持标题。另外 regenerateResponse / editAndResend 会把假消息之后的历史 slice 掉，点击"重新生成"即静默截断历史。

去重逻辑在任何真实输入下都失效。本地存原始 content，后端回传的是 normalizeForInvoke(processedMessage) 的结果——换行、工作区引用、附件三种常见场景下字符串必然不等，去重分支永远走不到。

01根因：输入与回流的语义被合并

claude 引擎以 --input-format stream-json 走 stdin 输入，CLI 会把用户消息原样回显到 stdout，两者在解析侧是同一个 StreamEvent::User，无法区分。

// claude.rs:736 — 输入（Polaris 主动写入 stdin）
stdin.write_all: {"type":"user","message":{"role":"user","content":[{"type":"text","text":message}]}}

// claude.rs:1037 — 回流（CLI 写 stdout，同一个 StreamEvent::User）
for ai_event in parser.parse(raw_event) { event_callback(ai_event) }

// event_parser.rs:656 — parse_user_event：对 text 块无差别处理
// 1. tool_result 块 → ToolCallEnd      ← 这一步有语义判断
for item in content { if item.type == "tool_result" { ...ToolCallEnd... } }

// 2. 文本内容 —— 没有任何来源判定，无差别发出
let text = self.extract_text_content(&message);   // join 所有 type:"text"
if !text.is_empty() { results.push(UserMessageEvent::new(...)) }
结构不对称：同一个函数里，tool_result 分支有明确的类型判断并路由到正确的事件；紧跟其后的 text 分支却没有任何判断就直接当作"用户消息"发出。注释里的编号 // 2. 提取文本内容 也说明作者只把它当作"顺手提取"，而非一个语义决策点。这一处是整个缺陷的源头——它决定了 user_message 事件同时承载"真实用户输入"和"claude CLI 的 user-role 回流"两个不可分辨的语义。

02去重为何必然失效

// eventHandler.ts:368 — 提交新增的去重
const lastUser = [...existing].reverse().find((m) => m.type === 'user')
if (lastUser && lastUser.content === content) break   // 仅比对最后一条，且要求完全相等

本地 addMessage 存的是原始 content（createConversationStore.ts:1706）；发给后端的是 normalizeForInvoke(processedMessage)（:1841），后端再原样塞进事件。三条路径各自改写字符串：

含换行的消息最常见
normalizeForInvoke（conversationStoreUtils.ts:238）执行 text.replace(/\n/g, '\\n')——把真实换行替换成字面反斜杠-n，并 .trim()。本地存真实 \n，后端回传字面 \\n，必然不等。
工作区引用高频
parseWorkspaceReferences 把 @name:src/App.tsx / @/src/App.tsx 改写成绝对路径 @D:/space/base/Polaris/src/App.tsx。本地存原始写法。
带附件条件触发
build_message_with_attachments（commands/chat.rs:347）把消息包成「嵌入内容 + 原文 + 文件引用列表」，用 \n\n 拼接。
第二个结构性缺陷：find 只在最后一条 user 消息上比对。即使内容碰巧相等，只要中间插入了另一条 user 消息，去重即失效。而假消息的注入恰恰会插入 user 消息。

另：makeStore 替身用 Object.assign 模拟 store，与真实 set((state)>…) 的响应式契约脱节；「存储层验证」那个用例只断言 backend.kind === 'remote'，不验证任何与修复相关的行为。这些测试对真实 store 的契约无约束力。

06方案对比

方案 A
前端收口：加来源标记字段
UserMessageEvent 增 source（client / echo / internal），前端仅渲染 source==='client'；删除现有 content 去重。
代价：改后端 3 处产生点 + 前端 1 处。遗留：claude 侧仍需在 parse_user_event 判定"这条是不是真用户输入"，否则 echo 与 internal 无法区分。
方案 B · 推荐
产生端消歧 + 首条回显去重
在 parse_user_event 判定：含 tool_result 的 user 事件不发 text 事件；text 与 tool_result 混合时不发；仅 text 块且为本轮首个 user 事件时发。claude 引擎的"首条 user 事件即回显的用户输入"是稳定可判定的边界。
代价：只改 event_parser.rs 一处。顺带：前端 content 去重可以整段删除，不再需要猜字符串相等。风险：依赖"Claude Code stream-json 模式下首条 user 事件即输入回显"这一行为，需实测锁定。
方案 C
语义拆分：新增 system 类型消息
把内部回流渲染为 type:'system' 的折叠提示，保留可观测性。
阻塞：ChatMessageType 虽定义 'system'，但全仓无任何代码生产 system 消息——无渲染器、无历史恢复、无导出分支。走这条路要先补整套基础设施，不是加一个 case 能解决的。
推荐 B，并同步删掉前端去重。去重逻辑的失败不是实现粗糙，而是它承担的职责不该由它承担——"哪条消息属于用户"必须由产生端声明，消费端猜字符串等长在这条链路上没有收敛路径。方案 C 保留了可观测性但基础设施缺口大，可作为 B 落地后的二期。

07验收标准

含换行的用户消息：claude 引擎下本地不出现第二条气泡，重载会话后仍为一条
工作区引用消息：@workspace:path 改写后本地与回流内容不一致，仍不重复渲染
带附件消息：build_message_with_attachments 包装后，用户气泡只出现一次
工具调用轮次：含 tool_result 的 user 事件不产生任何用户气泡（这是最直接的回归验证点）
会话标题：长会话中插入多次工具轮次后，标题仍取真实首条用户输入
重新生成：对任意一条 AI 回复点击重新生成，假气泡前后历史完整保留，不发生截断
JSONL 无假条目：会话文件里 type:"user" 条数等于真实发送轮数
simple_ai 路径：提交原有的多设备同步能力不回退（B 设备可见 A 的消息）
