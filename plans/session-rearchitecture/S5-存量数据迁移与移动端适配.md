# S5 — 存量数据迁移 + 移动端适配（spec）

> 状态：提案 · 归属：数据迁移 + 移动端 · 依赖：S1-S4 完成

---

## 1. 目标

- 将既有 JSONL 会话（历史归档）与新的 SQLite 权威投影接通：`externalId ↔ sessionId ↔ conversationId` 映射收敛到后端一张表，旧会话可恢复、可继续、不丢。
- 移动端（`polaris-mobile` / `polaris-pocket`）复用同一投影协议，不再维护独立的会话实现。

## 2. 现状（已核实）

- `src/services/dialogStorage/service.ts`：JSONL 按 `externalId`（文件名）归档消息；无 `sessionId` 维度。
- 后端 `dialog_index.rs`：已有 JSONL ↔ 会话索引的雏形。
- `polaris-mobile` / `polaris-pocket`：独立会话实现（不在主仓库路径内，需协调）。

## 3. 目标设计

### 3.1 映射表（后端唯一权威）

```sql
CREATE TABLE IF NOT EXISTS session_mapping (
  session_id      TEXT PRIMARY KEY,   -- 前端 sessionId（投影主键）
  conversation_id TEXT NOT NULL,      -- 后端引擎 conversationId
  external_id     TEXT,               -- 旧 JSONL 文件名/URI（可为空）
  workspace_key   TEXT NOT NULL,
  created_at      INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_session_mapping_ext
  ON session_mapping(external_id);
```

- **写入**：新会话创建 → 映射即建（backend 命令负责）；迁移旧 JSONL → 迁移脚本建映射。
- **读取**：前端/订阅拿 `sessionId`；恢复历史 → 由后端按 `external_id` 反查。

### 3.2 迁移脚本（一次性，可重入）

```text
输入：既有 JSONL 目录（按 externalId 枚举）
流程：对每个 externalId
  1) 读 dialog meta → conversationId/title/workspace
  2) 若无映射 → 建 session_id（可复用旧 conversationId 派生）+ 投影行（status=idle）
  3) 消息体原样入 session_messages（若 S1 落地消息入 SQLite 的决策为「是」）；否则仅登记映射
  4) 幂等：已迁移的不重复
输出：迁移报告（成功/失败/跳过）
```

### 3.3 移动端适配

- `polaris-mobile` / `polaris-pocket` 通过 HTTP+WS 连同一后端：
  - 会话列表 = `session_list_workspace`（S1）
  - 订阅 = `session_subscribe` + resync（S3）
  - 操作 = `session_send` / `session_interrupt`（S4，带 deviceId）
- 移动端可保留精简 UI，但**不再有自己的会话持久层**；断线时本地只缓存投影快照。

## 4. 验收

| # | 场景 | 验收 |
|---|---|---|
| 1 | 旧 JSONL 会话 | 迁移后可打开、历史消息完整、可继续对话 |
| 2 | 迁移可重入 | 重复跑不产生重复会话/消息 |
| 3 | 新会话映射 | 创建即入库，不依赖旧归档 |
| 4 | 移动端 | 列表/订阅/发送/中断与桌面一致 |
| 5 | 会话恢复 | 恢复操作不丢任何历史消息 |

## 5. 风险

- **迁移正确性**：需先做只读 dry-run 报告，人工核对后再执行；脚本写日志。
- **externalId 语义**：旧文件名可能是 `conversationId` 或 `uuid`，迁移脚本需兼容两种命名。
- **移动端协同**：不在主仓库的移动端需同步协议文档；提供 `session-api.md` 供其实现。
- **删除语义**：JSONL 归档若删除后仍被旧引用 → 映射保留但标记 `archived`，前端不展示。
