# 会话消息存储统一重构 — spec

> 状态：Phase 0-4 已完成评估与实施 · 归属：前端 + 后端 · 依赖：`session_messages`（已投产）、`dialog_index`（已投产）
> 动机：用户实测发现「读取会话历史时看到重复的 AI 回复（2~N 份相同）」，根因是多套消息存储/读取实现叠加 + 消息 id 漂移 + 去重契约不完整，导致磁盘重复自我繁殖。本 spec 决定**完全重构消息存储链路**，消除多套实现并存。

---

## 0. TL;DR

把 Polaris 会话消息存储从「前端 JSONL 独写 + 后端 SQLite 兜底 + localStorage 旧版 + OPFS 遗留 + session-v2 对账（未接线）+ session_state 投影（回退残留）」**六套并存**收敛为**单一权威链路**：

```
消息真相：后端 session_messages（SQLite，每 id + version 不可变日志）
  ├─ 写入：turn_persist（事件权威，adopt 前端 id）
  ├─ 归档：archive_conversation（唯一的 JSONL 写入方，只读派生层）
  └─ 查询：dialog_index（历史列表/搜索，只读派生层）

前端 store：只是 session_messages 的内存视图（Reconcile 对账）
  ├─ 流式渲染：currentMessage（id 从后端 adopt，不再 generateUUID）
  ├─ 轮末：不写 JSONL（后端归档唯一负责）
  └─ 恢复：只读 JSONL（不再 mergeBackendMessages，不再读 localStorage）
```

**核心原则**：一条消息只有一个 id，由消息创建方分配，全链路复用；一个存储只有一份真相，其余都是只读派生。

## 2. 每套实现为什么这么设计 + 踩了什么坑

### 2.1 JSONL 归档（A）— 前端整体覆写

**为什么**：v3 阶段从 IndexedDB 迁到 JSONL（`9e339f98`），解决「对话错乱」——整存整取、幂等、保序、无损存储完整 ChatMessage（含 blocks/attachments）。

**坑**：
- **双写**：前端轮末写（富块完整），后端兜底也写（派生版，缺富块）。S6 spec（`5f041713`）刻意设计为「只追加比归档更新的消息」，但当 id 不一致时，后端消息被当成新条目追加 → 重复。
- **流式快照残留**：旧 checkpoint 机制（`3d9d95ba`）会写 `isStreaming:true` 的中间快照；`5f041713` 移除了 checkpoint 但磁盘上的快照行没被清理 → 同 id 双行（流式版 + 完成版）。

### 2.2 后端消息库（B）— 事件权威

**为什么**：S6（`5f041713`）解决「客户端中途关闭时回复丢失」。后端监听 AI 事件流，节流落库 SQLite，轮末兜底归档。

**坑**（S6 spec 第 1 行直接承认）：
> **初版设计（消息 id 两端统一 + 前端 canonical 回写 + 归档删除链 + 全量读路径改造）过度复杂，已按「最小改动」重做。**

刻意跳过了「id 两端统一」，代价就是今天的问题：后端 `Turn.message_id` 自造 `xxx#axxx`（`turn_persist.rs:276`），前端 `createCurrentAssistantMessage` 用 `generateUUID()`（`createConversationStore.ts:231`）——**两套 id 体系并存**，`mergeBackendMessages` 按 id 求差时把后端消息当成新条目追加 → 重复。

**实测证据**（dev 数据根 `simple-ai-1791719649123-130.jsonl`）：同一轮回复在磁盘上有 4 行、3 个不同 UUID，全部 `ts=11:54:15`（同一秒），内容完全相同：
```
seq=1  id=b045bc1d  isStreaming=True   ← 流式快照（旧 id）
seq=2  id=41b1597c  isStreaming=False  ← 完成版（新 id）
seq=3  id=41b1597c  isStreaming=False  ← 同 id 再写一次
seq=4  id=3bdf9456  isStreaming=False  ← 又一个新 id
```

### 2.3 localStorage 旧版（D）

**为什么**：v1 阶段最简单的存储——`event_chat_session_history` 存轻量历史。

**坑**：被保留为降级兜底，但**已无写入者**（主路径早已走 JSONL）。`listNativeHistory` 和 `loadMessagesForItem` 仍读它，可能返回旧的、压缩过的内容 → 数据不一致。

### 2.4 session_state 投影（F）

**为什么**：S1-S5 跨端同步链（`55e1df1a` ~ `527abade`）——后端权威投影 + workspace 分桶 + 跨端订阅/广播。

**坑**：整个 S3 链被回退（`f5dc3c68`，15 个提交），但 `session_state.rs`（75KB）、`session_state_commands.rs`、`session_index_check.rs` **代码全留着**。回退不彻底 → 死代码 + 认知负担。

### 2.5 session-v2 对账

**为什么**：S3 的前端侧——Reconcile 对账（日志即真相，前端只是缓存）。

**坑**：S3 回退后，`reconcile.ts` + `v2-kernel.ts` 的 `resyncSession` 仍在，被 9 个文件引用，但**未接入 UI 主路径**——前端仍用 `sessionStoreManager` + `createConversationStore`（2535 行）作为真相。新旧并存。

### 2.6 appendConversationMessages（死设计）

**为什么**：`3d9d95ba`（流式 checkpoint 中断保护）设计 WAL 式增量追加——消息完成即落盘，崩溃最多丢半条。

**坑**：`5f041713` 移除了 checkpoint 机制（增量职责后移后端），但 `appendConversationMessages` 的实现、测试、`persistedSeq` 字段、`dedupMessages.ts` 的 checkpoint 注释**全留着**。无生产调用点 → 死代码 + 认知负担。

## 3. 重复的自我繁殖机制（已实证）

```
某次异常（id 漂移 / 旧 checkpoint / 恢复+续写）
  → 磁盘 JSONL 留下同内容不同 id 的多行
  → 恢复读取（parseDialogLines 按 id 去重，不同 id 不收敛）
  → store.messages 被污染（3 条同内容不同 id）
  → session_end 整体覆写（saveDialog 把污染的 messages 原样写回）
  → 磁盘重复持续 / 自我繁殖
  → mergeBackendMessages 按 id 求差（后端 id ≠ 前端 id 时追加）
  → 重复进一步增加
```

## 4. 重构目标

### 4.1 单一权威链路

- **消息真相**：后端 `session_messages`（SQLite，`PK(id, version)` 不可变日志 + 链式修订）
- **唯一 JSONL 写入方**：后端 `archive_conversation`（从消息库导出，前端不再写 JSONL）
- **历史查询**：`dialog_index`（派生，可重建）
- **前端 store**：只是 `session_messages` 的内存视图（Reconcile 对账 + 流式渲染）

### 4.2 消息 id 单一权威

- **id 由消息创建方分配**：前端 `currentMessage` 创建时分配 id（或后端事件首次到达时分配）
- **后端 adopt 前端 id**：`turn_persist` 不再自造 `xxx#axxx`，从事件/请求参数 adopt 前端 id
- **全链路复用同一 id**：流式快照、完成版、归档、消息库、索引——同一轮回复同一 id

### 4.3 删除死路径

- `appendConversationMessages`（无生产调用点）
- localStorage 旧版历史读取（`event_chat_session_history`）
- `session_state.rs` + `session_state_commands.rs` + `session_index_check.rs`（S3 回退残留）
- OPFS 迁移（`opfsMigration.ts`，无新数据）
- `dedupMessages.ts` 的 checkpoint 相关注释与残留逻辑

### 4.4 去重契约完整化（过渡期）

在 id 统一完成前，读取/保存的去重必须收敛「同内容不同 id」：
- `parseDialogLines`：id 去重 + 内容指纹去重
- `saveConversation`：写出前内容指纹归一

这不是补丁——是**去重契约的应有之义**（id 去重只处理同 id 多行，不处理同内容不同 id，本身就不完整）。

## 6. 与原设计的关系

| 原设计决策 | 本方案的态度 |
|---|---|

## 7. 风险

- **Phase 2（id 统一）改协议**：需同步后端 Rust + 前端类型 +（如涉及）插件。协议无运行时 schema 校验是已知缺口（AGENTS.md §4.1），改动需保守。
- **Phase 3（前端不写 JSONL）**：改变保存契约，需确保后端 `archive_conversation` 在所有引擎的 `SessionEnd` 都被调用（含异常退出路径）。
- **历史数据**：Phase 0 的去重对现有污染文件立即收敛，但物理重复行仍在磁盘（不清理，只读取时收敛）。如需物理清理，写一次性迁移脚本。
