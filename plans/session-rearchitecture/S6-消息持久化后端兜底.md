# S6 — 消息持久化后端兜底（spec）

> 状态：已实施（简化版）· 归属：后端（src-tauri）+ 前端恢复侧补读 · 依赖：`session_messages`（已投产）
> 修订：初版设计（消息 id 两端统一 + 前端 canonical 回写 + 归档删除链 + 全量读路径改造）**过度复杂**，
> 已按「最小改动解决客户端中途关闭丢回复」重做，见下文。

---

## 1. 问题

AI 回复到一半时**客户端**（web / 移动端）关闭 → 该轮回复无人落盘、恢复时看不到。
根因：**归档（JSONL）只有一个写入方——前端**（轮末 `saveDialog` 整体覆写）。前端不在场 ⇒ 无人写。

SimpleAI 尤其严重：其流式回复只走 `AIEvent::Token`，前端 checkpoint 之外的任何「按事件落盘」都没有覆盖它。

## 2. 目标（只做这一件事）

客户端中途关闭时，**该轮（含已输出的部分）仍进入归档**，任意端重新打开可见完整会话；覆盖所有引擎。

不做（刻意收敛，避免过度设计）：两端消息 id 统一、前端 canonical 回写、消息库读路径改造、删除链、多端仲裁。

## 3. 方案：前端仍是主写入方，后端做**兜底**写入方

```
AI 引擎事件流（engines 全局）
  │
  ▼  ai_chat_core 事件回调（start / continue 两条路径，覆盖全部引擎）
turn_persist::observe(event, engine)
  ├─ 本轮首事件到达          → 落库「本轮用户请求」（见 §3.1）
  ├─ Token / AssistantMessage / Thinking / ToolCall*
  │       └─ 累加「当前轮」blocks，节流 revise（isStreaming:true）→ session_messages（SQLite）
  └─ SessionEnd              → 落定（isStreaming:false）+ **兜底归档**（见 §3.2）

前端（不变）
  ├─ 轮末 saveDialog：整体覆写 JSONL（内容最完整：富块/附件/表单卡片）← 常规写入方
  └─ 恢复：读 JSONL；若本轮尚未归档（客户端中途关闭），
            用 loadBackendMessages(message_read) 补出消息库里那一轮
```

**关键取舍**：归档内容保真由**前端**负责（它才有 diff/附件/表单等富信息）；后端只在
「前端不在场」时补一份**派生版**（文本/思考/工具三类块；恢复时前端会为 Edit 工具回填 diffData）。
两者都写时以「只追加比归档更新的消息」收敛，不会互相覆盖。

### 3.1 用户请求按「事件会话 id」落库

实测（claude-code --print，2026-10-15）：`start` 的**返回值不是事件流使用的会话 id**
（返回 temp id；事件带引擎真实会话 id；前端最终以事件 id 作为 `conversationId`）。
且 claude-code **不发 SessionStart、不回显 user 事件**。

因此：`start` 入口只 `record_user_request(content, clientMessageId)` 登记；
该轮**首个事件到达**时（`observe` 里 `flush_pending_user_request`）才落库——
此时拿到的是事件会话 id，必然与会话下的 assistant 消息同属一个 `conversation_id`。
（队列上限 4、30s 过期，避免引擎启动失败的登记被后续轮次误认领。）
`continue` 的会话 id 已知，直接落库。

### 3.2 兜底归档规则（保守，不覆盖）

`turn_persist::archive_conversation(conv)`：
读既有 JSONL（含 legacy 行）→ 读消息库（每 id 最新版）→
**只追加 `timestamp > 归档最后一条时间` 的消息** → 按时间重排 seq → 重写 meta + 行。

- 前端已写过本轮 ⇒ 归档里已有更晚的消息 ⇒ 天然 no-op（不覆盖、不重复）。
- 前端不在场 ⇒ 本轮（用户 + assistant，含被中断的部分）补齐。
- 不删除、不重排既有内容 ⇒ 重新生成 / 编辑重发等前端内部行为不会被后端「复活」干扰
  （这类场景前端随后会整体覆写，胜出）。

### 3.3 崩溃恢复

后端启动：`recover_pending_turns()` —— 消息库中残留 `isStreaming:true` 的消息
（后端进程被强杀在回复途中）→ 落定为中断态 + 补一次兜底归档。

## 4. 验收（实测）

| 场景 | 结果 |
|---|---|
| 无任何客户端在场，`cap.ai.chat start` 一轮 → 消息库 + 归档 | ✅ 用户回答 + assistant 回复同会话、归档完整（`messageCount=2`，title/firstUser 正确） |
| 紧接 `continue` 第二轮 | ✅ 同会话追加，归档 4 条、顺序正确 |
| 既有 JSONL 会话继续对话 | ✅ legacy 消息保留、按时间追加、meta 的 workspacePath/createdAt/tokenUsage 沿用 |
| 旧版前端（JSONL 主写入方）行为 | ✅ 未改动：`saveDialog` 逻辑原样恢复 |

## 6. 已知代价（如实记录）

- 客户端中途关闭的那一轮，归档是**派生版**（无 diff/附件/表单卡片等富块）；
  这些富信息只在前端在场时完整——属信息源约束，非实现缺陷。
- 后端在 `SessionEnd` 同步做一次归档写盘（含历史索引重建）；大会话该轮末会有一次
  数十~数百 ms 的写盘开销（与旧前端 `saveDialog` 同量级，只是搬到了后端）。
- 客户端重开于「流式进行中」时，已输出部分要等该轮结束进入归档（或由消息库补读）才完整。
