# Polaris 会话体系完全重构 — 总纲（spec v1）

> 状态：提案（未实现）· 决策稿
> 读者：会话域 / 前端 / 后端 / 移动端协作者
> 关联：`AGENTS.md` §3.2/§3.3/§4.1/§4.2/§4.3，既有 `plans/session-management-zcode-alignment.md`
> 参考实现：`temp/ZCode/packages/{services/src/session, ui/src/store, client/src, shared/src}`

---

## 0. TL;DR

把 Polaris 会话体系从 **「前端进程内存真相 + JSONL 落盘 + 单一活跃会话」** 重构为 **「后端权威投影 + workspace 分桶 + 跨端订阅重放」**（对齐 ZCode 的 sessions-index / conversation 投影模型），使 **web / 桌面 / 移动任意端可同时查看与操作同一会话**。

现状已核实：后端权威底座（`session_state.rs`、`session_db.rs`、`cap.ai.chat`、`src/session-v2/` 内核）**已存在但未接入 UI 主路径**；前端 `sessionStoreManager` + `createConversationStore`（2535 行）仍是真相所在。

---

## 1. 现状诊断（已核实）

### 1.1 数据流现状

```text
[桌面进程]                                    [web/移动进程]
sessionStoreManager(Map)                     sessionStoreManager(Map)
   └─ activeSessionId 全局单一                  └─ activeSessionId 全局单一
   └─ stores[sessionId].messages/running       └─ stores[sessionId].messages/running
        ▲ 事件按 _routeSessionId 路由                ▲ 事件按 _routeSessionId 路由
        │                                              │
    EventRouter(单例)                            EventRouter(单例)
        ▲ chat-event                                ▲ chat-event
        │ IPC                                       │ HTTP/WS
   ┌────┴─────────────── 同一后端 ──────────────┴────┐
   │  cap.ai.chat / session_state / dialog JSONL    │
   └────────────────────────────────────────────────┘
```

- **真相在前端内存**：`messages` / `isStreaming` / `error` 各进程独立，JSONL 只落消息与 meta。
- **事件只进发起进程**：另一进程无该 `sessionId` 的 store → `dispatchEvent` 直接丢弃（`log.warn('事件未匹配到会话，丢弃')`）。
- **无 workspace 分桶**：多窗口/多端切换会话互相覆盖（`switchSession` 改单一 `activeSessionId`）。
- **后端权威已建但闲置**：`session_state.rs`（事件日志 + 仲裁 + Session Registry）、`session-v2` 前端内核均有，但 UI 主路径未接入；`V2SessionKernel.subscribe` 用 **1s setInterval 轮询** 兜底，非真正订阅。

### 1.2 根因（架构，非单一 bug）

1. **会话真相进程私有** → 跨端不可见。
2. **单一活跃会话** → 多窗口/多端互相覆盖。
3. **无跨端投影** → 另一端无法感知新建/删除/运行态。
4. **仲裁未接入** → 两端同时发送/中断会竞态。

## 2. 目标架构

### 2.1 总体数据流（目标）

```text
                    ┌─────────────────────────────────────────────────┐
                    │             后端（src-tauri，唯一权威）          │
                    │                                                 │
                    │  session-v2/messages.db (SQLite)               │
                    │   ├─ session_events   (append-only, seq)       │
                    │   ├─ session_records  (Session Registry, CAS)  │
                    │   ├─ session_messages (消息 JSON 列)            │
                    │   └─ sessions-index  (workspace 级投影, 新)     │
                    │                                                 │
                    │  cap.ai.chat (RouterBus)                       │
                    │  chat-event 广播（已有通道, 跨端统一）           │
                    └───────▲───────────────────────────▲────────────┘
                            │ IPC / HTTP+WS             │ IPC / HTTP+WS
                    ┌───────┴────────┐          ┌───────┴────────┐
                    │ 桌面进程         │          │ web/移动进程    │
                    │ SessionStore   │          │ SessionStore   │
                    │ (workspace桶)   │          │ (workspace桶)   │
                    │ 投影=后端权威    │          │ 投影=后端权威    │
                    └────────────────┘          └────────────────┘
```

核心不变量（对齐 ZCode `AGENTS.md` / SKILL 治理）：
- **单一事实源**：SQLite 是会话真相；前端 store 只是「按 workspace 分桶的投影缓存」。
- **单一写入路径**：所有变更走后端命令（`session_request_start` / `session_append_message` / `session_event_append`），前端不双写。
- **显式时序**：每条会话事件带 `seq`（后端分配）+ `deviceId`，跨端按 seq 因果收敛；resync 只补缺失，不覆盖新事件。
- **幂等**：append `INSERT OR IGNORE`（已有）；resync 按 id 去重（已有）。

### 2.2 领域模型（新增/对齐）

```ts
// 会话投影（后端权威，前端只读）
interface SessionProjection {
  sessionId: string            // 前端 sessionId
  conversationId: string | null
  title: string
  status: 'idle' | 'running' | 'error' | 'none'
  seq: number                  // 跨端因果序（后端分配）
  updatedAt: number
  workspaceId: string | null
  engineId: string
  lastError: string | null
  startedByDevice: string | null   // 运行中由哪个端发起
  modelProfileId?: string
  model?: string
  agent?: string
}

// workspace 级会话索引（新增，对齐 ZCode sessions-index）
interface WorkspaceSessionsIndex {
  workspaceKey: string          // identity ?? path（对齐 ZCode resolveWorkspaceStateKey）
  sessions: SessionProjection[]
  version: number               // 列表变更版本（驱动 UI 刷新）
}
```

- 协议变更需 **Rust `models/ai_event.rs` + 前端 `src/types/` 双向同步**（AGENTS.md §4.1）。
- 保守原则：只加字段、不改既有枚举；`sessionId`（前端）与 `conversationId`（后端引擎）双轨保留。

## 3. 方案全景（5 个子方案）

| # | 子方案 | 范围 | 依赖 |
|---|---|---|---|
| S1 | **后端会话权威收敛** | `session_state.rs` 补 `sessions-index`（workspace 级投影 + 增量帧 + seq）；`cap.ai.chat` 补 `session_subscribe`；协议加 `sessions_index_frame` | 无 |
| S2 | **前端 SessionStore 重构（workspace 分桶）** | 拆 `createConversationStore`（2535 行）+ `sessionStoreManager` → 对齐 ZCode `zcodeSessionStore*` | S1 |
| S3 | **跨端投影订阅** | 前端 `subscribeWorkspaceSessions`（首拉快照 + 增量帧 + gap repair）；替换 `V2SessionKernel.subscribe` 轮询 | S1,S2 |
| S4 | **统一仲裁与命令入口** | 发送/中断/继续/重试统一走 `cap.ai.chat` + 后端仲裁；前端不本地自决 | S1,S2 |

每份子 spec 含：目标、接口、状态机、验收、风险。实现顺序 **S1 → S2 → S3 → S4 → S5**，每阶段一个 PR + 一组 vitest + 一次 `cargo check`。

## 4. 关键设计决策

### 4.1 workspace key：`identity ?? path`（对齐 ZCode）

```ts
export function resolveWorkspaceStateKey(workspacePath: string, workspaceIdentity?: string): string {
  return workspaceIdentity?.trim() || workspacePath
}
```

- 身份隔离（SSH/WSL/Docker/远程）用 `identity`，本地 fallback 用 `path`。
- 状态写入只写 identity 桶；path 桶仅作本地 fallback 和迁移起点（对齐 `zcodeSessionStoreSelectors.updateWorkspaceState` 的注释纪律，防远程串台）。

### 4.2 订阅语义：桌面 continuous / 移动 replayable（对齐 ZCode AGENTS.md §进程协议）

```text
desktop: continuous  ── 直接 live stream ──┐
                                           ├─ 同一 owner + sequence
mobile:  replayable ── snapshot + gap repair ┘
```

- `session_subscribe(workspaceKey, afterSeq)`：返回 `{ snapshot, lastSeq }` + 增量帧流（`chat-event` 通道复用）。
- 断线重连：`session_subscribe_resync(workspaceKey, lastSeq)` 补增量；gap 过大回退全量快照。
- 帧带 `topic`（`conversation/<id>` / `sessions-index/<wsKey>`），前端按 topic 分流（对齐 ZCode `onDynamicSessionsIndexFrame`）。

### 4.3 仲裁（对齐 ZCode CommandInbox / owner-lease）

- 发送前 `session_request_start(conversationId, deviceId)`：已 running → 拒绝（返回 reason）。
- 中断 `session_request_interrupt(conversationId, deviceId)`：deviceId 校验；无权限 → 拒绝。
- 前端 `interruptSession` / `sendMessage` **不再本地自决**，统一走 `cap.ai.chat` + 后端仲裁。
- 保留幂等：同 `requestId` 重试不双写（AGENTS.md §4.2 记忆 `ai-chat-interrupt-continue-root-cause`）。

### 4.4 消息真相：JSONL 保留为「历史归档」、SQLite 为「活跃会话真相」

- 活跃会话（含流式中）：SQLite `session_messages`（权威）。
- 历史归档：现有 JSONL `dialogStorageService` 保留（不动写入方），作为只读恢复源与迁移源。
- 两套映射：`sessionId ↔ conversationId`、`conversationId ↔ externalId(JSONL 文件名)` 收敛到后端一张表，前端不重复维护。

## 5. 验收标准（端到端）

| 编号 | 场景 | 验收 |
|---|---|---|
| A1 | 桌面开会话 A，web 打开 | web 看到 A 的 running/idle 状态与桌面一致（<2s） |
| A2 | 桌面发送消息 | web 实时收到流式块，不丢事件 |
| B1 | 桌面看 A、web 看 B | 两端互不覆盖（无串台） |
| B2 | 切换 workspace | 各自草稿/运行态独立 |
| C1 | 桌面新建/删除会话 | web 列表自动增删（无需刷新） |
| C2 | 断线重连 | 增量补齐，不重复、不丢事件 |
| D1 | 两端同时发送 | 仅一端成功，另一端收到明确拒绝原因 |
| D2 | 两端同时中断 | 仅一端成功，状态一致收敛到 idle |
| E1 | 旧 JSONL 会话迁移 | 历史会话可恢复、可继续（映射不丢） |
| E2 | 移动端打开同一会话 | 状态与桌面一致，可操作 |

## 7. 风险与边界

- **协议漂移**：改 `models/ai_event.rs` + 前端类型必须同 PR；无运行时 schema 校验是已知缺口，本次保守（只加字段）。
- **巨文件**：`createConversationStore.ts`（2535 行）是 S2 主触点，**按 AGENTS.md 只拆新增改动常触碰的部分**，不做无收益全量重构。
- **中断竞态**：S4 必须保留幂等与顺序语义（`requestInterrupt` 返回 reason）。
- **存量兼容**：旧 JSONL ↔ 新投影映射必须收敛到后端一张表，前端不双写。
- **本机验证**：`cargo test --lib` 不可用（Tauri DLL 限制），后端用 `cargo check`；前端 `pnpm typecheck` + vitest。
- **发布门控**：动命令层/协议必跑 `cargo check --no-default-features --bin polaris-web --bin polaris-mcp`（AGENTS.md §3.4）。

## 9. 决策（已定稿，依据 `01-评审决策.md`）

实现前已多角度自评定稿，结论如下：

1. **消息存储**：保留现有 `session_messages` 表（已投产）为消息真相；历史 JSONL 归档留 S5。S1 仅建会话投影，不改消息。
2. **订阅通道**：S1 交付**拉取式** `session_index_list/_after` 快照与增量查询（数据源）；广播帧留 S3 复用现 WS（按 event 名订阅 + seq 去重 + resume，底座已具备）。
3. **workspace key**：对齐 ZCode `identity ?? path`，由命令参数 `workspaceKey` 显式传入后端，后端不猜测。
4. **轮询兜底**：本次不动（S3 前端改造时再移除）。
5. **迁移范围**：本次不做 JSONL 迁移（S5）；存量 `session_records` 不自动 backfill 入投影，由前端/迁移显式 `session_index_register`。

> ⚠️ **关键约束**（评审发现）：`session_state.rs` 与 `session_db.rs` 共用同一 `messages.db` 文件，各自独立用 `PRAGMA user_version`（2 vs 1）做「版本不一致 → 删库重建」。因此任何新增表的 schema **禁止触版本号升级**，一律用 `CREATE TABLE IF NOT EXISTS` 幂等补建。
