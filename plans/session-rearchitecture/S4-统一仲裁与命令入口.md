# S4 — 统一仲裁与命令入口（spec）

> 状态：提案 · 归属：前端调度 + 后端仲裁 · 依赖：S1、S2

---

## 1. 目标

让 **发送 / 中断 / 继续 / 重试** 全部走 `cap.ai.chat` + 后端仲裁，前端不再本地自决；解决双端并发操作的竞态：同时发送仅一端成功、同时中断仅一端生效，失败方收到明确 reason。

对齐 ZCode：CommandInbox 串行 + owner/lease 仲裁；延续 `ai-chat-interrupt-continue-root-cause` 的教训（幂等 + 顺序）。

## 2. 现状（已核实）

- `src/services/aiChatDispatch.ts`（42 行）：已有 `cap.ai.chat` dispatch 入口，但**非唯一派发路径**，前端多处直接调用 transport/轮询内核。
- `src/services/transport/index.ts` / `detector.ts` / `httpTransport.ts`：transport 按环境二选一（tauri IPC vs HTTP/WS）。
- 后端 `session_state.rs`：已有 `request_start` / `request_interrupt` 仲裁雏形。
- `src/session-v2/`：`V2SessionKernel` 内部有快照合并，但 UI 层未统一走它。

## 3. 目标架构

### 3.1 统一命令入口（`cap.ai.chat` 命令面）

```ts
// 发送/继续
session_send({ conversationId, sessionId, messageText, body?, requestId })
  → { accepted: true, ticketId } | { accepted: false, reason: 'already_running' | 'invalid_conversation' }

// 中断
session_interrupt({ conversationId, sessionId, requestId })
  → { accepted: true } | { accepted: false, reason: 'not_running' | 'not_owner' | 'unknown_conversation' }

// 重试/继续（复用 send，带 resume 标记）
session_resume({ conversationId, sessionId, requestId, resumeFromSeq })
```

- 所有命令带 `deviceId` + `requestId`（幂等键）。
- 前端 `sendMessage / interruptSession / continueSession` 内部**只派发这些命令并等待 accepted 结果**，不再自行判定可发送性。

### 3.2 后端仲裁规则（对齐 ZCode owner-lease）

| 命令 | 规则 |
|---|---|
| send | 会话非 running 或 请求方为当前 owner → accepted；否则 `already_running` |
| interrupt | 会话 running 且 `startedByDevice == deviceId` → 停；否则 `not_owner`（或策略开关允许任何端停） |
| resume | 幂等：同 requestId / 同 resumeFromSeq 重复调用 → 直接 accepted(true, 原 ticket) |

- `startedByDevice` 在 `session_records.started_by_device`（已有字段位置：S1 投影含该列）。
- 中断与发送之间、两次并发发送之间：**串行队列**（对齐 CommandInbox），同一 conversation 的命令排队执行，避免竞态窗口。

### 3.3 前端不再做的自决（废除清单）

- ❌ 前端自行判断「能否发送」（旧：`canSendMessage` 纯本地状态）
- ❌ 前端直接调用 transport 层发送/中断（不再绕过 cap.ai.chat）
- ❌ 前端自造 `running=true` 然后等失败再回滚（改为：accepted 后乐观标记，帧到达为准）

保留：
- ✅ 乐观 UI（accepted=true 立即回显，对齐 ZCode 乐观合并；与 S3 帧冲突以帧为准）

## 4. 状态机（命令生命周期）

```text
UserAction → dispatch(cap.ai.chat, cmd, {requestId, deviceId})
   → 返回 accepted? 
      yes → 乐观应用 → 等待后端帧 (S3) 收敛
      no  → UI 显示 reason（例如 already_running → 提示另一端在运行）
重试/中断 同理，requestId 幂等
```

## 5. 验收

| # | 场景 | 验收 |
|---|---|---|
| 1 | 桌面正在运行 A，web 再发 | web 收到 `already_running`，不重排 |
| 2 | 两端同时按发送 | 仅一端 accepted，另一端明确 reason |
| 3 | 非 owner 中断 | 默认拒绝（可配置允许）；无副作用 |
| 4 | 同 requestId 重发 | 不双写，返回原 ticket |
| 5 | 中断后状态收敛 | 双端 status → idle，<2s 一致 |

## 6. 风险

- **行为变化**：前端不再自决会改变现有乐观体验 → 需给 UI 明确的 accepted/reason 反馈路径，避免「点了没反应」。
- **兼容**：移动端（polaris-pocket）若仍直连旧路径，需在同一 PR 切换到 cap 命令面（或保留旧接口过渡）。
- **幂等键**：requestId 需 UUID 且不跨请求复用；deviceId 需端级全局唯一（沿用现有端识别机制，未有则补）。
